# PLAN 0.13.86 — Role-scoped views of the evaluation / trace surface

> Citations: `docs/research/AgrentHarness2.md` (synchronization rule #4: Trace-visibility ↔ Role), PLAN 0.13.81 (scenario recording — `recorded_ops` + `Pipelines::Recorder::Translator`), PLAN 0.13.84 (harness-component metadata; `:evaluation`-tagged routes are the trace producers), PLAN 0.13.85 (`Current.actor` + Authorizable concern).

## Purpose

Every interaction in this codebase already produces something trace-shaped: a `Context` row, a `recorded_ops` entry on a scenario, a CI artifact in `docs/migrations/`, a spec example in `spec/`. None of those producers know who is allowed to look at what they recorded.

The harness paper's evaluation interface is the cross-cutting layer that observes Application / Harness / Platform. In a multi-role system, evaluation must project differently per audience: a Customer's trajectory recording is private to them and their support SDE; a Vendor's trajectory is private to them and Data; SDE sees everything; UX sees their own canvas-edit traces.

This plan ships the role-scoped projection. Trace producers stay unchanged; trace *consumers* see only the slice their role admits.

Depends on PLAN 0.13.81 being load-bearing in production (today the Ruby half ships but the recorder daemon mode is deferred to the harness PR), and on PLAN 0.13.85 having `Current.actor` populated everywhere. Schedule after both are stable.

## In Scope

- A `Trace` table (or a `Context` extension) carrying `actor_role`, `actor_session_id`, `tenant_id` alongside the existing payload.
- Trace producers tagged in PLAN 0.13.84 (`:evaluation`-tagged routes) write actor claims at emission time.
- Read scopes on `Trace`: `for_customer(session_id)`, `for_vendor(tenant_id)`, `for_role(role)`, `for_actor(Authz::Actor)`. Composable.
- Three trace views, role-gated:
  - `/my_activity` (Customer): their own session traces only.
  - `/tenant_activity` (Vendor): their tenant's traces only.
  - `/traces` (SDE / Data): the full surface, with role-and-tenant filters in the UI.
- Migration of the four highest-volume trace producers — `Context.create!`, `Scenario#recorded_ops` writes, canvas saves (PLAN 0.13.75), reindex runs (PLAN 0.13.82) — to populate the new actor columns.
- Audit spec: every `:evaluation`-tagged GlobalRoute (PLAN 0.13.84 metadata) emits a Trace row whose `actor_*` claims match `Current.actor` at call time.

## Out of Scope

- Trace retention / archival policy. v1 keeps everything indefinitely; retention is a separate plan.
- Per-attribute redaction (e.g., "Vendor sees their tenant's traces but with customer PII redacted"). Row-level only for v1, matching PLAN 0.13.85's row-level auth scope.
- Real-time streaming of traces to dashboards. v1 is request/query.
- Replaying a trace. PLAN 0.13.81 already does this for `recorded_ops`; this plan doesn't extend the replay surface.
- Cross-tenant analytics for SDE / Data. The `/traces` view shows scoped slices on demand; aggregate dashboards are a follow-on.

## Architecture

### Schema

Two paths considered; recommendation is the second:

**(A) New `Trace` table.** Clean separation; every `:evaluation`-tagged operation writes a Trace row. Pro: no churn on the existing Context model. Con: much of `Context`'s payload IS trace data; we'd be duplicating storage.

**(B) Extend `Context`** with actor-claim columns:

```ruby
class AddActorClaimsToContexts < ActiveRecord::Migration[8.1]
  def change
    add_column :contexts, :actor_role,        :string
    add_column :contexts, :actor_tenant_id,   :string
    add_column :contexts, :actor_session_id,  :string
    add_index  :contexts, [:actor_role, :created_at]
    add_index  :contexts, :actor_tenant_id
    add_index  :contexts, :actor_session_id
  end
end
```

`scenarios.recorded_ops_metadata` (PLAN 0.13.81) already carries `recorder_role` — fold that into the new column shape; migrate existing rows in-place.

Going with (B). Single trace surface; existing tooling unchanged.

### Producer-side change

Every `:evaluation`-tagged route, on entry, populates the actor columns from `Current.actor`:

```ruby
# In Operations::Base or similar
def emit_trace(payload)
  Context.create!(
    payload: payload,
    target: trace_target,
    publisher: trace_publisher,
    session_id: Current.actor.session_id,
    actor_role: Current.actor.role,
    actor_tenant_id: Current.actor.tenant_id,
    actor_session_id: Current.actor.session_id  # might equal session_id; both kept for clarity
  )
end
```

Exact shape depends on existing `Context.create!` call sites; the PR sequence covers a handful at a time.

### Read scopes

```ruby
class Context < ApplicationRecord
  scope :for_role,    ->(role)        { where(actor_role: role.to_s) }
  scope :for_tenant,  ->(tenant_id)   { where(actor_tenant_id: tenant_id) }
  scope :for_session, ->(session_id)  { where(actor_session_id: session_id) }
  scope :for_actor,   ->(actor) { for_role(actor.role).then { |s| actor.tenant_id ? s.merge(for_tenant(actor.tenant_id)) : s } }
end
```

### Three views

| Path | Role gate | Scope |
|---|---|---|
| `/my_activity` | any authenticated actor | `Context.for_session(Current.actor.session_id)` |
| `/tenant_activity` | `vendor` (or higher) | `Context.for_tenant(Current.actor.tenant_id)` |
| `/traces` | `developer` / `data_engineer` / `ai_developer` | unscoped, with role + tenant filter dropdowns |

The Customer view (`/my_activity`) is the privacy-preserving default — every actor can see what they themselves did, no more.

### Audit (closes the loop with PLAN 0.13.84 + 0.13.85)

```ruby
RSpec.describe "evaluation-tagged route trace emission" do
  GlobalRoute.by_harness_component(:evaluation).each do |route|
    it "#{route.procedure}: emits a Trace with Current.actor's claims" do
      with_actor(role: "customer", session_id: "spec-123") do
        execute_route(route)
      end
      expect(Context.last.actor_role).to eq("customer")
      expect(Context.last.actor_session_id).to eq("spec-123")
    end
  end
end
```

Forces every `:evaluation`-tagged route to actually carry the actor claim through to the trace row. Drift catch.

### Backfill

One-shot migration script `bin/backfill-trace-actors`:

- For existing `Context` rows where `actor_role` is null, fill from heuristics: `recorder_role` on the parent scenario; `publisher` field; or "unknown".
- Logged to `docs/migrations/trace-actor-backfill.txt` (matches the rerb-audit pattern).

2. **PR 2** — Producer-side: 3-4 high-volume trace emissions migrated to populate actor columns. The `:evaluation`-tagged audit spec wired up but tolerant of unmigrated routes.
3. **PR 3** — `/my_activity` view + Customer-scope request spec.
4. **PR 4** — `/tenant_activity` view + Vendor-scope request spec.
5. **PR 5** — `/traces` view + SDE/Data role gate + filter UI.

## Acceptance Criteria

- [ ] `Context` has `actor_role` / `actor_tenant_id` / `actor_session_id` columns with appropriate indexes.
- [ ] `Context` exposes `for_role` / `for_tenant` / `for_session` / `for_actor` scopes.
- [ ] Every `:evaluation`-tagged GlobalRoute (PLAN 0.13.84 metadata) emits Context rows with non-null `actor_*` claims.
- [ ] `/my_activity`, `/tenant_activity`, `/traces` all exist with their role gates.
- [ ] Customer A cannot read Customer B's traces. Vendor X cannot read Vendor Y's traces. Verified by request spec.
- [ ] `bin/backfill-trace-actors` ran once; the resulting log is committed.
- [ ] No regressions in scenario recorder, canvas save, or reindex specs.

## Follow-ups (Not This Plan)

- Trace retention policy + archival job.
- Per-attribute redaction in trace payloads (vendor analytics without customer PII).
- Real-time trace streaming to a dashboard surface (extends PLAN 0.13.81's recorder pattern in the opposite direction — emit instead of capture).
- Aggregate cross-tenant analytics for Data role.
- A "trace replay" view that lets SDE / Data step through a trajectory inline (extends PLAN 0.13.81's replay capability with a UI).
