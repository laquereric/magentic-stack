# PLAN_0_99_0 — Cross-branch search: parallel agentic + human substrate

> Research seed: [docs/research/cross-branch-search.md](../research/cross-branch-search.md)
>
> *"graph semantics allow a single repo file to exist simultaneously
> in several branches with parallel editing. use the existing
> infrastructure to implement this to support parallel agentic /
> human activity"*

## Answer to the framing question

**Can the substrate be branch-aware without becoming branch-managed?**
Yes — by treating each git branch as a *named graph* over the same
source files, with branch metadata propagating through every existing
retrieval surface (SPARQL, fts5, vec0, the MCB action layer). Git
remains the authority for what branches exist + what's in them; the
substrate is a *read-side projection* that fans out to the branches
git enumerates.

The pattern:

```
              ┌──────────────────────────────────────────┐
              │            git for-each-ref               │   ← source of branch truth
              │   (no branch state stored in substrate)   │
              └────────────────┬─────────────────────────┘
                               │
                  enumerate branches + their HEAD shas
                               │
   ┌──────────────────────────────────────────────────────┐
   │  graph:chunk: walk each branch via                    │
   │  `git show <branch>:docs/plans/PLAN_*.md` → chunks   │
   │  tagged with `meta.branch`                            │
   │                                                       │
   │  graph:extract: emit triples into named graphs        │
   │  `<urn:mm:branch:feature-foo>` per branch             │
   │                                                       │
   │  graph:fts:build: fts_chunks adds `branch` column     │
   └──────────────────────────────────────────────────────┘
                               │
              ┌────────────────┴────────────────┐
              ▼                                 ▼
       /sparql GRAPH ?b               /fts_search { branch: [...] }
       /hybrid_search { branch: [...] }
              │                                 │
              └─────────►  substrate_search MCB action  ◄─────────
                                  │
                ┌─────────────────┴─────────────────┐
                ▼                                   ▼
     Claude session A on worktree           Claude session B on worktree
        for branch-X                            for branch-Y
```

No new branch-state machinery in the substrate. Git tells us what's
out there; the substrate caches a per-branch projection.

## What's already in place that we leverage

| Component | What it gives us free | Reference |
|---|---|---|
| sqlite-sparql named graphs | Per-branch triple storage with no schema change | `vendor/sqlite-sparql/README.md` §"rdf_insert(s,p,o,graph)" |
| fts5 UNINDEXED columns | Add `branch` next to existing `corpus` column | recipe pattern from PLAN_0_98_x landed fts work |
| sqlite-vec | Vectors don't need branch awareness directly — fts/sparql filter on metadata; vec ranks within the resulting set | `docker/kg-server/server.rb` /hybrid_search |
| `git show <ref>:<path>` | Read file content from any branch without checkout — no worktree juggling for indexing | git plumbing |
| Manifest pattern (already landed for incremental chunking) | Per-branch fingerprint = (sha-at-HEAD, file-blob-sha-in-tree). When the branch's HEAD doesn't move, nothing to re-chunk. | `server/lib/tasks/graph.rake` `CHUNK_MANIFEST_PATH` |
| `substrate_search` MCB action | Add `branch:` to its input_schema; pass through to /hybrid_search | `server/packs/platform/.../substrate_search.rb` |

Roughly: this milestone is mostly **plumbing**, not new infrastructure.

## Slice breakdown (proposed)

Each slice gets its own ICE-frontmattered plan file when authored. Five
slices are the natural decomposition:

### Slice 1 — Per-branch chunking via `git show`

Update `graph:chunk` to iterate branches enumerated by
`git for-each-ref --format='%(refname:short) %(objectname)' refs/heads/`
(plus optionally `refs/remotes/origin/` with a flag). For each
`(branch, path)`, read content via `git show <branch>:<path>` instead
of filesystem read; chunk; tag `meta.branch`.

Manifest extended: key becomes `(branch, rel_path)`; fingerprint
becomes the blob sha at that tree position (perfectly stable and
git-native; no mtime games).

Writes: per-branch JSONLs OR a unified JSONL with `meta.branch`
column (the latter is simpler downstream — single fts.db ingest).

### Slice 2 — fts5 `branch` column + substrate_search filter

`fts_chunks` gains `branch UNINDEXED` (mirror of how `corpus` was
added in the prior fts work). `substrate_search` action's
`input_schema` gains `branch: { type: array, items: { type: string } }`.
Default: query against `main` (current behaviour).
`branch=*` or `branch=[]` empty = all branches.

### Slice 3 — Named-graph SPARQL projection

`graph:extract` emits N-Quads to `tmp/graph/derived.nq` where each
quad's fourth term is `<urn:mm:branch:<name>>`. Embedded turtle
blocks similarly wrap into named graphs. `vendor/sqlite-sparql`'s
`rdf_insert(s, p, o, graph)` is the existing seam.

`/sparql` queries with `GRAPH ?b { ... }` then enumerate branches.

### Slice 4 — vv-planning branch awareness

`vv_planning_plans` table gains a `branch` column (default 'main').
The unique constraint becomes `(plan_id, branch)` not just `plan_id`.
`Vv::Planning::Sync.from_markdown(path, branch: nil)` defaults to
'main' but accepts an override (eventually driven by the calling
context — a sync triggered from worktree X passes branch X).

### Slice 5 — Parallel-worktree workflow + branch GC

The substrate doesn't *create* worktrees — operators / scripts do.
But the substrate's tooling (bin/planrunner, the chunk pipeline)
should be safe to run in parallel from multiple worktrees:

- Manifest uses a `(branch, path)` key, not `path` alone → no
  cross-branch collisions
- Branch deletion (per `git for-each-ref`'s output, branch absent
  from prior run = deleted) triggers eviction of that branch's
  chunks + triples on next chunk pass
- Optional MCB action `mm.kg.branches` lists branches with last-
  indexed-HEAD + chunk count

## State model (no new events; one new vocabulary file)

This milestone introduces **no new RES events**. Git events
(branch-create, branch-delete, branch-update) are not RES — they're
read-on-demand via `git for-each-ref`.

One new vocab file: `server/config/vocab/branch.ttl` with:

```turtle
@prefix mm: <https://magenticmarket.ai/vocab#> .

mm:Branch          a rdfs:Class .
mm:branchHead      a rdf:Property .  # branch → commit SHA
mm:branchOrigin    a rdf:Property .  # branch → upstream remote
mm:lastIndexedAt   a rdf:Property .  # branch → timestamp
mm:chunkBelongsTo  a rdf:Property .  # chunk → branch URI
```

## Safety invariants

1. **Git is the only branch authority.** The substrate never invents
   a branch. If `git for-each-ref` doesn't list it, it doesn't
   exist as far as we're concerned.
2. **Read-only against branches.** `graph:chunk` uses `git show`,
   never `git checkout`. No worktree state is touched.
3. **Branch deletion is silent + eventually consistent.** When a
   branch disappears, its chunks evict on the next chunk pass; no
   error if a query lands during the gap.
4. **Default branch behaviour is unchanged.** Without a `branch=`
   filter, substrate_search returns main's results (today's
   semantics).
5. **No cross-branch write coupling.** Two sessions on two
   worktrees never block each other; the substrate is read-side
   projection only.

## Drift / rollback signals

- `fts.db` has a `branch=X` row where `git rev-parse X` returns
  not-found → stale branch leak, GC needs to run.
- Branch count × corpus size growing the fts.db beyond ~500 MB →
  index pruning policy needed (probably "branches older than 30d
  with no commits beyond their merge-base get a slim index").
- Two parallel sessions both chunk the same branch at the same
  time → manifest race. Probably acceptable (last-writer-wins,
  both wrote the same content), but worth a single-writer lock if
  observed.
- Vector store size — 4096-dim vectors × N branches × M chunks
  blows up fast. Probably means vec index stays main-only and
  branch-aware queries skip vec, using fts + named-graph SPARQL
  for cross-branch.

## Out of scope (this milestone)

- **Conflict resolution / merge-time automation.** This milestone
  surfaces conflicts (two branches edit the same chunk); resolving
  them stays human.
- **Branch authorisation.** Operator-level access control over
  who can read which branch's projection is a separate concern.
- **Push hooks / GitHub Actions integration.** Branch indexing
  runs on operator / planrunner cadence, not on every push.
- **Cross-fork / cross-repo branches.** Only local branches +
  remote-tracking branches in this repo are indexed.

## Prerequisites for going live

1. **PLAN_0_98_0/_1 transport work is landed** (or stable enough
   that branch-awareness can be added on top).
2. **Incremental chunking is live** (already landed in commit
   `ad24ff0`) — branch-aware chunking is a natural extension of
   that manifest.
3. **vv-planning v0.1.0 schema is firm** — Slice 4's branch column
   is the first real schema change; needs the gem stable enough
   to migrate.

## Exit criteria (milestone "done")

- All five slices land their own ICE-frontmattered plans + ship.
- A demo session: two operators (or one operator + one Claude)
  work in parallel on two worktrees with two distinct feature
  branches. A SPARQL query against `/sparql` enumerates both
  branches' live state. substrate_search with `branch=…` returns
  the right slice of the corpus per session.
- Stale-branch eviction is observable: delete a branch, run the
  chunk pass, query for it → 0 results.
