# PLAN 0.11.0 — Unified Input Processing: One Pipeline, Three Speeds

## The Problem

User input flows through 7 different processing paths, each with its own parser, executor, and latency profile:

| Path | Parser | Latency | Added in |
|---|---|---|---|
| BNF1 ElementAction | `parseElementAction()` (JS) | <1ms client | Original |
| BNF2 InventoryDbQuery | `InventoryDbQueryParser` (Ruby) | ~100ms server | 0.10.12 |
| BNF3 ComponentRender | `ComponentRenderParser` (Ruby) | <1ms server | 0.10.12 |
| Legacy commands | `"target:command(args)"` regex in `parseElementAction` | <1ms client | Original |
| Ad-hoc patterns | `CONFIRM_PATTERNS`, `GREETING_PATTERNS`, `ESCALATE_PATTERNS` regex | <1ms server | 0.10.15–22 |
| Fuzzy/vector resolve | `OntologyResolver` Levenshtein + sqlite-vec | 1–50ms server | 0.10.15 |
| LLM fallback | `AgentRouter` + `LlmService` | 2–10s server | Original |

A developer adding a new feature has to know: Which path will my input hit? Which parser applies? Where does execution happen? What format do I use — BNF1, BNF2, legacy, or ad-hoc regex?

There's no single entry point, no shared dispatch model, and no consistent way to know what happened. The `OrchestrationBus` log helps but only covers the server side. Client-side BNF1 execution is invisible to the server.

### Developer Experience Issues

1. **No single place to add a command.** Want to add a "compare" action? You need: a BNF1 command in `runCommand` switch, a handler function, a command string on the button, and if it needs server data, a WAMP call. Four files, three languages.

2. **No visibility into what path ran.** The user types "yes" — was that CONFIRM_PATTERNS → re-send, or Tier A LLM? The server log shows OrchestrationBus phases, but the client has no trace.

3. **Latency is unpredictable.** Same input box, vastly different response times: "Printers" = 100ms (Tier C), "What's your return policy?" = 5s (Tier A LLM), "yes" = 100ms (confirm) or 5s (LLM fallback). The user gets no indication which path was taken until the response arrives.

4. **Three BNF grammars share infrastructure but not dispatch.** `BnfBaseParser`, `BnfTokenizer`, and `GrammarParser` exist. But BNF2 is only called from `QueryFirstResponder`, BNF3 is only emitted as metadata, and BNF1 is only parsed client-side. There's no unified "parse this, route it, execute it" pipeline.

5. **Testing requires knowing the path.** The RSpec specs test each component in isolation. But a developer can't write one test that says "when the user types X, assert Y happens" without knowing which of the 7 paths X will take.

## Latency Tiers

The key architectural constraint: response latency determines UX. Three tiers:

| Tier | Latency | What runs | UX expectation |
|---|---|---|---|
| **Instant** | <10ms | Client-side BNF1 parse + execute, DOM updates, state dispatch | Immediate visual feedback |
| **Fast** | 10–200ms | Server-side classify, plan, BNF2 query, Triple lookup, template | Loading indicator optional |
| **Slow** | 1–10s | LLM inference, vector embedding, augmentation | Thinking indicator required |

The unified pipeline should make the latency tier explicit — the developer declares which tier a command runs in, and the framework handles the UX (instant response, loading state, thinking indicator).

## Three Approaches

### A: Command Registry — One Dispatch Table, Three Executors

Replace the 7 paths with a single command registry. Every input — text, button click, BNF program, confirmation — resolves to a command. Commands declare their executor (client, server-fast, server-slow) and the registry dispatches accordingly.

**Registry:**

```javascript
// lib/command_registry.js
const CommandRegistry = {
  commands: {},

  register(name, { executor, parse, latency }) {
    this.commands[name] = { executor, parse, latency }
  },

  resolve(input, context) {
    // Try each registered command's parse function
    for (const [name, cmd] of Object.entries(this.commands)) {
      const match = cmd.parse(input, context)
      if (match) return { name, ...cmd, args: match }
    }
    return null
  },

  async execute(input, context) {
    const cmd = this.resolve(input, context)
    if (!cmd) return { routed: false }

    // Show appropriate UX for latency tier
    if (cmd.latency === "slow") context.showThinking()
    else if (cmd.latency === "fast") context.showLoading()

    try {
      const result = await cmd.executor(cmd.args, context)
      return { routed: true, command: cmd.name, result }
    } finally {
      context.hideIndicators()
    }
  }
}
```

**Registration examples:**

```javascript
// Client-instant commands
CommandRegistry.register("nav.go", {
  latency: "instant",
  parse: (input) => {
    const m = input.match(/^(?:\d+\s+DO\s+)?nav\.go\s+(.+)/i)
    return m ? { url: m[1] } : null
  },
  executor: ({ url }) => { window.location = url }
})

CommandRegistry.register("right.collapse", {
  latency: "instant",
  parse: (input) => input.match(/right\.collapse/i) ? {} : null,
  executor: () => document.dispatchEvent(new CustomEvent("mm:panel:state", { detail: { state: "collapsed" } }))
})

// Server-fast commands (BNF2 product query)
CommandRegistry.register("product.search", {
  latency: "fast",
  parse: (input, ctx) => {
    const cats = OntologyResolver.extractCategories(input) // client-side would need a simple version
    return cats.length > 0 ? { message: input } : null
  },
  executor: async ({ message }, ctx) => {
    return ctx.wamp.call("mm.ai.chat", { session_id: ctx.sessionId, message, role: "user" })
  }
})

// Server-slow commands (LLM)
CommandRegistry.register("ai.chat", {
  latency: "slow",
  parse: () => true, // catches everything
  executor: async ({ message }, ctx) => {
    return ctx.wamp.call("mm.ai.chat", { session_id: ctx.sessionId, message, role: "user" }, { timeout: 120000 })
  }
})
```

**Single entry point:**

```javascript
// In chat_controller.js send():
async send() {
  const text = this._activeInput()?.value?.trim()
  if (!text) return
  this._transitionToConversation()
  input.value = ""

  this.state.dispatch({ type: "chat:send", text, displayName: this.displayNameValue })

  const context = { sessionId: this.sessionValue, wamp: this.wamp, state: this.state,
    showThinking: () => this._showThinking(), showLoading: () => this._setStatus("Loading..."),
    hideIndicators: () => { this._hideThinking(); this._setStatus("") }
  }

  const result = await CommandRegistry.execute(text, context)
  // Result handling...
}
```

**Developer experience:**

Adding a new command = one `CommandRegistry.register()` call with `parse`, `executor`, and `latency`. No need to know about OrchestrationBus, BNF parsers, or the 7 processing paths.

```javascript
// Example: adding a "compare" command
CommandRegistry.register("product.compare", {
  latency: "fast",
  parse: (input) => {
    const m = input.match(/compare\s+(\w+)\s+(?:vs|and)\s+(\w+)/i)
    return m ? { a: m[1], b: m[2] } : null
  },
  executor: async ({ a, b }, ctx) => {
    return ctx.wamp.call("mm.product.compare", { skus: [a, b], session_id: ctx.sessionId })
  }
})
```

**Tracing:**

```javascript
CommandRegistry.execute = async function(input, context) {
  const cmd = this.resolve(input, context)
  console.log(`[Command] ${cmd?.name || 'unresolved'} latency=${cmd?.latency} input=${input.substring(0, 40)}`)
  // ...
}
```

**Pros:**
- One entry point for all input — `CommandRegistry.execute(input, context)`
- Latency tier is declared, not discovered — UX indicators automatic
- Adding a command is one function call, not 4 files
- Client-side tracing shows which command ran
- BNF1/2/3 become registered commands, not special cases

**Cons:**
- Client-side registry can't do server-side classification (OntologyResolver) — needs a fast client approximation or a round-trip
- Resolve order matters — more specific parsers must register before catch-all
- Migrating all 7 paths to the registry is a large refactor
- Server-side OrchestrationBus still needed for bid/quality/augment logic

**Effort:** ~10 hours (registry + migration of all paths + tracing + latency UX)

### B: Tiered Pipeline — Client Resolves Instant, Server Resolves Fast/Slow

Split the pipeline into two phases. Phase 1 runs client-side (<10ms): parse BNF1 commands, check local patterns (confirm, greeting), resolve obvious product terms from a cached category list. Phase 2 runs server-side only if Phase 1 didn't resolve: full OrchestrationBus with classification, planning, bidding, execution.

**Client-side resolver (Phase 1):**

```javascript
// lib/input_resolver.js
const InputResolver = {
  // Cached category list — loaded once from server
  categories: [],

  resolve(input, context) {
    // 1. BNF1 program?
    if (input.match(/\d+\s+DO\s+/) || input.includes(":")) {
      const { ast } = parseElementAction(input)
      if (ast.length > 0) return { type: "bnf1", ast, latency: "instant" }
    }

    // 2. Greeting?
    if (input.match(/^\s*(hi|hello|hey|thanks)\s*[!?.]?\s*$/i)) {
      return { type: "greeting", latency: "instant" }
    }

    // 3. Confirmation of suggestion?
    if (input.match(/^\s*(yes|yeah|ok|sure)\s*[!?.]?\s*$/i) && context.lastSuggestion) {
      return { type: "confirm", category: context.lastSuggestion, latency: "fast" }
    }

    // 4. Known product category? (from cached list)
    const words = input.toLowerCase().split(/\s+/)
    const match = words.find(w => this.categories.includes(w) || this.categories.includes(w.replace(/s$/, "")))
    if (match) return { type: "product", category: match, latency: "fast" }

    // 5. Unresolved — send to server
    return { type: "server", latency: "slow" }
  }
}
```

**Chat controller uses the resolver:**

```javascript
async send() {
  const text = this._activeInput()?.value?.trim()
  if (!text) return

  const resolution = InputResolver.resolve(text, {
    lastSuggestion: this._lastSuggestion
  })

  switch (resolution.type) {
    case "bnf1":
      // Execute immediately, no server round-trip
      resolution.ast.forEach(node => this._executeCommand(node))
      return

    case "greeting":
      // Respond instantly with canned greeting
      this.state.dispatch({ type: "chat:send", text, displayName: "You" })
      this.state.dispatch({ type: "chat:message", payload: {
        publisher: "ai", text: "Hello! How can I help?", display_name: "AI"
      }})
      return

    case "confirm":
    case "product":
      this._setStatus("Loading...")
      // Fall through to server, but expect fast response
      break

    case "server":
      this._showThinking()
      break
  }

  // Server round-trip
  this.state.dispatch({ type: "chat:send", text, displayName: "You" })
  this._sendToAi(text)
}
```

**Category cache loaded on connect:**

```javascript
// In connect():
fetch("/.well-known/mm/ontology").then(r => r.json()).then(data => {
  InputResolver.categories = data.categories || []
})
```

**Server stays unchanged.** OrchestrationBus still handles all server-side processing. The client just pre-resolves obvious cases to show appropriate UX.

**Developer experience:**

Adding a client-resolved command = add a case to `InputResolver.resolve()`. Adding a server command = add to OrchestrationBus (unchanged). The boundary is clear: instant = client, everything else = server.

**Tracing:**

```javascript
const resolution = InputResolver.resolve(text, context)
console.log(`[Input] type=${resolution.type} latency=${resolution.latency} input=${text.substring(0, 40)}`)
```

**Pros:**
- Clear latency boundary: client instant vs. server fast/slow
- Client resolver is simple — pattern matching on cached data, no grammar parsing
- Server pipeline unchanged — no migration needed
- Greeting/confirmation handled instantly without server round-trip
- Category cache makes product detection fast (<1ms)

**Cons:**
- Two resolvers (client + server) with potential disagreement — client says "product", server says "converse"
- Category cache can be stale — new categories need a refresh
- Fuzzy/typo correction still needs the server (Levenshtein on full synonym table)
- Doesn't unify BNF2/3 into the client pipeline — they remain server-only

**Effort:** ~5 hours (InputResolver + category cache + send() rewrite + tracing)

### C: Grammar Router — BNF as the Universal Input Format

Every input is parsed as a BNF program before dispatch. The three grammars (BNF1, BNF2, BNF3) plus natural language become four input modes. A Grammar Router tries each parser in priority order, scores the result, and dispatches to the appropriate executor.

**Principle:** If the input is parseable as a BNF program, execute it as one. If not, treat it as natural language and send to OrchestrationBus.

**Grammar Router (server-side):**

```ruby
class GrammarRouter
  GRAMMARS = [
    { name: :element_action, parser: ElementActionParser, executor: :execute_bnf1, latency: :instant },
    { name: :inventory_db_query, parser: InventoryDbQueryParser, executor: :execute_bnf2, latency: :fast },
    { name: :component_render, parser: ComponentRenderParser, executor: :execute_bnf3, latency: :fast }
  ].freeze

  def self.route(input, session_id:)
    # Try each grammar in order — first valid parse wins
    GRAMMARS.each do |grammar|
      result = grammar[:parser].parse(input)
      next unless result.valid? && result.score >= 0.7

      Rails.logger.info "[GrammarRouter] #{grammar[:name]} score=#{result.score} input=#{input.first(40)}"
      return {
        grammar: grammar[:name],
        ast: result.ast,
        score: result.score,
        latency: grammar[:latency],
        executor: grammar[:executor]
      }
    end

    # No grammar match → natural language → OrchestrationBus
    { grammar: :natural_language, latency: :slow, executor: :execute_orchestration }
  end

  def self.execute(route, session_id:, message:)
    case route[:executor]
    when :execute_bnf1
      # BNF1 is client-side — return the AST for client execution
      { type: "bnf1", ast: route[:ast].map(&:to_h), execute_on: "client" }
    when :execute_bnf2
      # Execute query against Triple store
      results = QueryFirstResponder.send(:execute_query, route[:ast])
      ChatResponseTemplate.from_query(message, results, session_id: session_id)
    when :execute_bnf3
      # Component render — return render instructions
      { type: "bnf3", ast: route[:ast].map(&:to_h), execute_on: "client" }
    when :execute_orchestration
      OrchestrationBus.respond(session_id, message, role: "user")
    end
  end
end
```

**Integration into OrchestrationBus:**

```ruby
def self.respond(session_id, message, role: "user")
  # Try grammar route first
  route = GrammarRouter.route(message, session_id: session_id)

  if route[:grammar] != :natural_language
    log "GRAMMAR  #{route[:grammar]} score=#{route[:score]} latency=#{route[:latency]}"
    return GrammarRouter.execute(route, session_id: session_id, message: message)
  end

  # Natural language path — existing pipeline
  log "NATURAL_LANGUAGE  falling through to OrchestrationBus"
  # ... existing Phase 1-5 ...
end
```

**Developer experience:**

Adding a new command = write a BNF grammar (or extend an existing one). The grammar defines the syntax; the executor defines the behavior. The router handles dispatch, scoring, and latency.

```ruby

  def parse_statement(tokens, line_num)
    # COMPARE sku VS sku ON dim,dim
    # ...
  end
end

# Register
GrammarRouter::GRAMMARS << {
  name: :compare_query, parser: CompareQueryParser,
  executor: :execute_compare, latency: :fast
}
```

**Client receives `execute_on: "client"` flag:**

```javascript
// In _sendToAi response handler:
if (result.execute_on === "client" && result.type === "bnf1") {
  result.ast.forEach(node => this._executeCommand(node))
  return
}
```

**Tracing — unified log:**

```
[GrammarRouter] element_action score=1.0 input="10 DO nav.go /product/EPET2850"
[GrammarRouter] inventory_db_query score=0.95 input="10 FIND printer IN bhphoto"
[GrammarRouter] natural_language falling through to OrchestrationBus
[OrchestrationBus] INPUT session=marketplace message="What's your return policy?"
[OrchestrationBus] CLASSIFY categories=[] confidence=0.0 method=none
[OrchestrationBus] PLAN strategy=converse
[OrchestrationBus] BID tier=A confidence=0.95
[OrchestrationBus] EXECUTE tier=A
```

**Reward-based routing:**

The `BnfBaseParser.reward()` method already returns a 0-1 score. The Grammar Router uses this: if BNF2 scores 0.95 for "Printers", it routes to the fast query path. If it scores 0.3 for "What's your return policy?", it falls through to natural language. The score IS the routing decision.

```ruby
GRAMMARS.each do |grammar|
  score = grammar[:parser].reward(input)
  next unless score >= 0.7
  return { grammar: grammar[:name], score: score, ... }
end
```

**Pros:**
- BNF grammars are the universal abstraction — every input is scored against every grammar
- `reward()` makes routing a scoring problem, not a cascade of if-else
- New grammars plug into the router with one registration
- Server-side GrammarRouter log shows exactly which grammar matched and at what score
- Latency is grammar-determined — BNF1 = instant, BNF2 = fast, NL = slow
- The existing `GrammarParser.detect_and_parse()` already does format detection — this extends it

**Cons:**
- Parsing every input against 3+ grammars adds ~5ms server-side overhead
- Natural language (the most common input) always fails all grammars before falling through
- BNF1 is client-side but GrammarRouter is server-side — round-trip for instant commands
- Requires users to type BNF syntax directly (or the system generates it from NL)
- The grammars are designed for machine-generated programs, not human-typed input

**Effort:** ~8 hours (GrammarRouter + integration + registration + client execute_on handling + tracing)

## Comparison

| | A: Command Registry | B: Tiered Pipeline | C: Grammar Router |
|---|---|---|---|
| **Where it runs** | Client-side registry | Client resolve + server execute | Server-side router |
| **Input format** | Any (pattern matchers) | Any (pattern + cache) | BNF or natural language |
| **Latency model** | Declared per command | Resolved per input | Grammar-determined |
| **Add a command** | `register()` call (JS) | Case in resolver (JS) or OrchestrationBus (Ruby) | New grammar class (Ruby) |
| **Tracing** | Client console log | Client console log | Server Rails log (unified) |
| **Migration cost** | High — rewrite all 7 paths | Low — client overlay, server unchanged | Medium — add router before OrchestrationBus |
| **Instant commands** | Client-only, no round-trip | Client-only, no round-trip | Requires server round-trip |
| **Server-side scoring** | No | No | Yes — `reward()` based routing |
| **Effort** | ~10 hours | ~5 hours | ~8 hours |

## Recommendation

**B now, C next.**

Tiered Pipeline (B) is the fastest path to a better developer experience. It adds a client-side resolver that handles the obvious cases (BNF1 commands, greetings, confirmations, known categories) instantly, without touching the server. The server pipeline stays unchanged — OrchestrationBus, ConversationPlanner, and the BNF parsers continue to work as they do. The boundary is clear: instant = client, everything else = server.

This solves the worst DX problem immediately: latency visibility. The client knows the tier before the server call, so it shows the right UX indicator. Adding a client-resolved pattern is one line. Adding a server command is unchanged.

C (Grammar Router) is the right long-term architecture. Making `reward()` the universal routing function — every input scored against every grammar — is elegant and extensible. But it only works when the grammars are mature enough to score natural language input correctly. Today, typing "Printers" would fail BNF1 (not a command), fail BNF2 (not a structured query), fail BNF3 (not a render spec), and fall through to NL. The grammar scores don't help until the system generates BNF programs from NL input (which requires an LLM pre-pass, adding latency).

A (Command Registry) is the cleanest abstraction but the highest migration cost. It replaces everything — the 7 paths become N registered commands. Worth building after B validates the tiered model and C proves grammar-based routing.

### Implementation Order (Approach B)

1. **InputResolver** — client-side resolver with pattern matchers for BNF1, greeting, confirm, known categories (~1.5 hours)
2. **Category cache** — load from `/.well-known/mm/ontology` on connect (~30 min)
3. **send() rewrite** — use InputResolver to determine latency tier, show appropriate indicator (~1 hour)
4. **Client tracing** — `console.log("[Input]")` with type, latency, input preview (~15 min)
5. **Server tracing** — OrchestrationBus log already exists; add Grammar Router log when C is built (~15 min)
6. **Documentation** — developer guide: "Adding a new command" with examples for each tier (~30 min)
7. **Tests** — RSpec for category cache endpoint, client-side jest/vitest for InputResolver (~1 hour)
