# PLAN 0.13.52 — /data Endpoint: CRUD Operations and ERD Visualization

## Context

The `/rails_source` MVC browser shows fetched values for a route — `@scenario (Scenario)`, `@slide (Slide)` with their attributes. But the developer can only read. There's no way to edit a record, see its relationships visually, or navigate the data graph from the editor.

The data layer is the connective tissue between all roles:
- The UX Developer's intentions are data (Intention records)
- The AI Developer's configs are data (OrchestrationConfig records)
- The User's scenarios are data (Scenario → Slide → SlideRegion → Context)
- The Designer's styles reference data (Context payload → component → CSS)

A `/data` endpoint makes the data layer directly navigable, editable, and visualizable.

## Three Approaches

### Approach A: Record Browser with Inline Editing

A simple model/record browser. Select a model, see its records, click a record to view/edit its fields and navigate associations.

```
/data                                    → model index
/data?model=Scenario                     → records list
/data?model=Scenario&id=27              → record detail + edit
/data?model=Slide&id=122&assoc=scenario → navigate to parent
```

**Implementation:**

```ruby
# DataController
def show
  @model_class = params[:model].safe_constantize

  if params[:id]
    @record = @model_class.find(params[:id])
    record_detail
  else
    records_list
  end

```

**Tradeoffs:**
- Simple — table views with click-to-navigate
- No visual ERD — relationships are text links
- Good for inspecting and editing individual records
- Familiar pattern (like Rails Admin or Avo)

```
/data                                    → ERD diagram
/data?model=Slide                        → ERD + records panel
/data?model=Slide&id=122                → ERD + record detail
```

The ERD is rendered as SVG or HTML/CSS boxes with lines. Model positions are fixed (not auto-layouted). Clicking a model box highlights it and opens the records panel below.

**Implementation:**

The ERD uses MvcEntry model metadata (associations) to draw boxes and arrows:

```ruby
def erd_data
  MvcEntry.models.map do |entry|
    {
      name: entry.name,
      slug: entry.slug,
      associations: entry.metadata["associations"] || [],
      fields: extract_fields(entry),
      record_count: entry.name.safe_constantize&.count || 0
    }
  end
end
```

**Tradeoffs:**
- Visual — developers see the data model at a glance
- ERD + record browser in one view
- SVG/HTML layout requires positioning logic
- More effort than Approach A
- The ERD is the most useful artifact for onboarding new developers

### Approach C: GraphQL-Style Explorer with Live Queries

A query builder that lets the developer write and execute queries against the data model. Think GraphiQL but for ActiveRecord. The developer types a query, sees results, and can drill into associations.

```
/data                                    → query editor
/data?query=Slide.find(122).slide_regions → execute query
```

```
┌──────────────────────────────────────────────────────────────────┐
│  Data Explorer                                                    │
├────────────┬─────────────────────────────────────────────────────┤
│ MODELS     │  QUERY                                               │
│            │  ┌─────────────────────────────────────────────────┐ │
│ Scenario   │  │ Slide.find(122)                                 │ │
│ Slide      │  │   .slide_regions                                │ │
│ SlideRegion│  │   .includes(:context)                           │ │
│ Context    │  │   .map { |sr|                                   │ │
│ Intention  │  │     { region: sr.region,                        │ │
│ CogTier   │  │       component: sr.context.ui_component["name"]│ │
│ OrchConfig │  │     }                                           │ │
│ Actor      │  │   }                                             │ │
│            │  └─────────────────────────────────────────────────┘ │
│            │  [Run]                                               │
│            │                                                      │
│            │  RESULT                                              │
│            │  [                                                   │
│            │    { region: "right", component: "ChatPanel" },     │
│            │    { region: "main", component: "CategoryGrid" }    │
│            │  ]                                                   │
│            │                                                      │
│            │  2 records, 3 queries, 4ms                            │
└────────────┴─────────────────────────────────────────────────────┘
```

**Implementation:**

```ruby
def execute_query(query_string)
  # Sandbox: only allow read operations on allowed models
  ALLOWED_MODELS = %w[Scenario Slide SlideRegion Context Intention
                      CognitiveTier OrchestrationConfig Actor MvcEntry].freeze

  # Parse and validate the query starts with an allowed model
  model = query_string.split(".").first
  return { error: "Not allowed" } unless ALLOWED_MODELS.include?(model)

  # Execute in a read-only transaction
  result = ActiveRecord::Base.transaction do
    ActiveRecord::Base.connection.execute("PRAGMA query_only = ON") if ActiveRecord::Base.connection.adapter_name == "SQLite"
    eval(query_string) # sandboxed by model whitelist + read-only transaction
  end

  { result: result, queries: count }
end
```

**Tradeoffs:**
- Most powerful — arbitrary queries with full ActiveRecord API
- Dangerous — `eval` requires careful sandboxing
- Best for debugging — "show me all contexts where publisher = ai and payload includes 'printer'"
- Not visual — no ERD, no drag-and-drop
- Security risk without proper sandboxing

## Recommendation

**Start with A** (Record Browser). Simplest, most useful immediately. Click through models and records, see associations as links, edit fields inline.

**Layer B** (ERD) on top. Generate the diagram from MvcEntry model metadata. The ERD is the landing page; clicking a model opens the record browser from A.

**Treat C** (Query Explorer) as a power-user tool behind a flag. The `eval` sandboxing needs careful design. Useful for debugging but risky for production.

```
Week 1:  Approach A — Record browser with association navigation
Week 2:  Approach B — ERD diagram from MvcEntry metadata
Later:   Approach C — Query explorer (development only, behind flag)
```
