# PLAN_0_153_4 — Lift doctrine rule predicates code→graph

v0.1 (PLAN_0_153_2) hard-coded the doctrine rule predicates in
Ruby inside Harness::Loss::DoctrineRunner (frozen-string-literal
missing, Dry::Monads present, CommonJS require / module.exports).
This slice moves those predicates into urn:mm:doctrine as
triples so the rule SET, not just the rule body, is
graph-authored. The runner becomes a thin interpreter.

Closes the next step on `[[feedback-mcb-context-from-graph]]`:
context + checks both flow from the graph.

## Shape

### Vocabulary extension

  urn:mm:vocab/Rule              rdf:type for rule subjects
  urn:mm:vocab/belongsToDoctrine doctrine id (string)
  urn:mm:vocab/ruleId            rule local id (string)
  urn:mm:vocab/ruleKind          'first_line_must_match' |
                                 'must_be_absent' |
                                 'must_match'
  urn:mm:vocab/rulePattern       Ruby regex source (string)
  urn:mm:vocab/ruleMessage       human-readable description

Rule subject IRI: `urn:mm:doctrine:<doc-id>:rule:<rule-id>`

### Catalog

Each entry gains a `rules:` field — an array of
  { id:, kind:, pattern:, message: }

Seeded rules:
  ruby-1
    - frozen_string_literal·first_line_must_match·'\A# frozen_string_literal: true'
    - dry_monads_absent    ·must_be_absent·'Dry::Monads'
    - success_monad_absent ·must_be_absent·'\bSuccess\s*\('
    - failure_monad_absent ·must_be_absent·'\bFailure\s*\('
  javascript-1
    - no_commonjs_exports ·must_be_absent·'^\s*module\.exports\s*='
    - no_commonjs_require ·must_be_absent·'(^|[^.\w])require\s*\('

### Persister

seed! / propose: writes one INSERT DATA per triple, then for each
rule in the entry, writes the Rule subject triples too. .decide
is unchanged.

### Lookup

all_entries now joins rules per doctrine. Each returned entry
includes `rules: [{ id, kind, pattern, message }, ...]`.
Lookup uses a second SPARQL query keyed off ruleId / belongs‐
ToDoctrine and merges into the entry hashes.

### Loss::DoctrineRunner

No more if-trees. Pure interpreter:
  entries = Harness::Doctrine.for_path(path)
  entries.flat_map { |e| (e[:rules] || []).select { |r| violates?(r, content) } }

  violates? dispatches by rule[:kind]:
    first_line_must_match  → first meaningful line ~ pattern? false=violation
    must_be_absent         → content ~ pattern?            true =violation
    must_match             → content ~ pattern?            false=violation

Unknown kinds never trigger violations (guidance, not crash).

## Acceptance

1. The existing 10-example doctrine_runner_spec still passes
   verbatim (same expected scores).
2. lookup_spec for the ruby entry now includes `rules:` array
   with the four ruby rules.
3. Adding a new rule to Catalog only requires editing Ruby
   data, not code (a clean test for the data/code separation).
