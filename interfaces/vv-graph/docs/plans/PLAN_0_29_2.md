# PLAN 0.29.2 — Semantica Gap 1: sqlite-vec + `neighbor` (vector ANN above the graph tier)

> *V0.29.x continues. PLAN_0_29_1 brought the substrate onto the [`vv-graph`](https://github.com/laquereric/vv-graph) + [`sqlite-sparql`](https://github.com/laquereric/sqlite-sparql) upstreams + added a Tier 0 graph-traversal layer (SPARQL via Oxigraph) to the `OntologyResolver` cascade. PLAN_0_29_2 closes Semantica.md's named Gap 1 — embedding-based ANN retrieval — by adopting a new upstream surface (`Semantica::Vector`, expected at `vv-graph` v0.2.0) that wraps `sqlite-vec` (C extension, Alex Garcia's successor to sqlite-vss) + the `neighbor` gem. Surface refinements continue to travel as upstream PRs; the substrate is the consumer. Substrate-side work: `Intention#guide_text_embedding` (1536-dim default; `MM_EMBEDDING_MODEL` env var configurable) populated by `WikiCompiler` during compile pass; `mm_semantica_nearest(query_text:, max_results:)` Mm::Tool exposes the vector lookup to AI Apps (auto-emitted via the V0.28.4 Kotlin generator; lockstep audit picks it up); the `OntologyResolver` cascade re-orders to Tier 0a (vector) → Tier 0b (graph) → Tier 1 (stem) → Tier 2 (fuzzy) → Tier 3 (LLM). No back-compat priority: the cascade re-ordering is a single commit; old fallback paths stay but their relative ordering is fixed by audit. Citations: [`../research/Semantica.md`](../research/Semantica.md) (Gap 1 section + the convergent-architecture frame), [`../research/RailsRustSqlite.md`](../research/RailsRustSqlite.md) (sqlite-vec via `neighbor`, Rails 8 native `extensions:` loading), [`PLAN_0_29_1.md`](PLAN_0_29_1.md) (the substrate's adoption of the gem this plan rides on), [`vv-graph` upstream README](https://github.com/laquereric/vv-graph#readme).*

## The strategic frame

Three observations land at the same point:

1. **The cascade is the natural surface to extend.** `OntologyResolver`'s Tier 1/2/3 has been the substrate's "natural-language → category" path; PLAN_0_29_1 added Tier 0 (graph) above. Adding Tier 0a (vector) on top of that — without re-architecting — is a single insertion, audit-locked.

2. **The bridge is already named.** `RailsRustSqlite.md` § 3.2 specifies the exact stack: `sqlite-vec` (C extension) + `neighbor` gem (ankane/neighbor — production-stable; the pgvector author's Rails surface). Rails 8's native `extensions:` config (already in use for sqlite-sparql per PLAN_0_29_1) loads both side-by-side without monkey-patching.

3. **The substrate's embedding workload is amortisable.** Embeddings get computed once at `WikiCompiler` time, written to the per-model column, and re-read on every lookup. The per-query cost collapses to a single SQLite call (HNSW-flavoured ANN over a few thousand rows is sub-millisecond at the substrate's catalog scale). The LLM dependency stays one-shot at compile-time, not per-request.

The strategic move: **route Gap 1 through the same gem boundary PLAN_0_29_1 built**, so the substrate continues to consume one Rails-side semantic layer (gem-mediated) rather than two parallel paths (one for SPARQL, one for vectors).

## Why no back-compat priority (load-bearing decision, inherited from PLAN_0_29_1)

Same doctrine; the cost case is the same:

- **The substrate is the only consumer of the cascade.** No outside operators depend on the Tier-ordering being stable.
- **The cascade is operator-internal.** AI Apps call `mm_semantica_nearest` (new) or rely on `OntologyResolver` opaquely; neither cares which tier hit.
- **Coexistence (old Tier-order + new Tier-order behind a flag) costs more than the migration.** The cascade re-ordering is a single commit; `git revert` is the rollback path.
- **Old fallback paths stay.** The point is the *ordering*, not deletion. Tier 1 (stem) / Tier 2 (fuzzy) / Tier 3 (LLM) all remain — their position in the cascade is what the audit locks.

If mid-Phase something blocks: stop at the last green phase + ship a follow-up. Don't ship a half-wired Tier 0a.

### Phase B — Per-model embedding column + migration

`Intention` gains `guide_text_embedding` via a `neighbor`-style migration generated through `rails generate neighbor:sqlite` (per `RailsRustSqlite.md` § 3.2):

```ruby
class Intention < ApplicationRecord
  has_neighbors :guide_text_embedding, dimensions: 1536
end

# Migration:
class AddGuideTextEmbeddingToIntentions < ActiveRecord::Migration[8.0]
  def change
    add_column :intentions, :guide_text_embedding, :vector, limit: 1536
  end
end
```

Dimension default is 1536 (matches OpenAI's `text-embedding-3-small`, the convergent reference's typical choice). Operators select a different model + dimension via `MM_EMBEDDING_MODEL` env var; the gem's `Semantica::Vector.embed` reads dimension from the model's response and the migration documents how to re-roll the column for non-1536 models.

`Intention#guide_text` is an existing accessor (concatenation of `name + content["wiki"]` derived during compile); the embedding column shadows it.

### Phase C — `WikiCompiler` embedding pass

`WikiCompiler.compile_all` already walks every Intention + recompiles `content["wiki"]` from triples. PLAN_0_29_2 extends the compile pass with a one-shot embedding step:

```ruby
def compile_all
  Intention.find_each do |intention|
    new_wiki = derive_wiki(intention)
    intention.update!(content: intention.content.merge("wiki" => new_wiki))

    # NEW: embedding pass — amortised at compile time, not per-query
    embed_result = Semantica::Vector.embed(intention.guide_text)
    if embed_result[:ok]
      intention.update!(guide_text_embedding: embed_result[:vector])
    else
      log_refusal(embed_result)
    end
  end
end
```

Failures are logged + tolerated (the cascade falls through to Tier 0b / 1 / 2 / 3 when embeddings are missing). The compile pass is the right place because:
- It already runs ad-hoc / on operator demand — the embedding cost rides the existing trigger.
- It batches naturally (one model load per N intentions instead of per-query).
- Operators see embedding refusals at compile time (loud, surfaced) instead of at runtime (silent fallback).

### Phase D — `mm_semantica_nearest` Mm::Tool subclass

New primitive in `Mm::Tool::Registry`; deterministic + interpreter_callable + no side_effects. Auto-emits to the Kotlin generator surface per V0.28.4 (the lockstep audit catches it).

```ruby
class Mm::Tools::SemanticaNearest < Mm::Tool
  primitive deterministic: true, interpreter_callable: true, side_effects: false

  def call(query_text:, max_results: 5)
    result = Semantica::Vector.nearest_by_text(
      model_class: Intention,
      column: :guide_text_embedding,
      query_text: query_text,
      max_results: max_results
    )
    return refusal(result) unless result[:ok]

    success(
      query_text: query_text,
      embedding_model: result[:embedding_model],
      matches: result[:results].map { |r| { intention_id: r[:record].id, name: r[:record].name, distance: r[:distance] } }
    )
  end
end
```

The Kotlin generator (V0.28.4) picks up the new subclass + emits the Android-side wrapper without manual intervention; the lockstep audit at `server/spec/architecture/sme_dge_audit_spec.rb` enforces parity.

### Phase E — `OntologyResolver` cascade update (single commit)

The cascade re-orders. Pre-PLAN: Tier 0 (graph) / Tier 1 (stem) / Tier 2 (fuzzy) / Tier 3 (LLM). Post-PLAN: Tier 0a (vector) / Tier 0b (graph) / Tier 1 (stem) / Tier 2 (fuzzy) / Tier 3 (LLM).

```ruby
def resolve(text)
  resolve_via_vector(text) ||    # Tier 0a — NEW
  resolve_via_graph(text)  ||    # Tier 0b — PLAN_0_29_1 (demoted one position)
  resolve_via_stem(text)   ||    # Tier 1
  resolve_via_fuzzy(text)  ||    # Tier 2
  resolve_via_llm(text)          # Tier 3
end

def resolve_via_vector(text)
  result = Semantica::Vector.nearest_by_text(
    model_class: Intention,
    column: :guide_text_embedding,
    query_text: text,
    max_results: 1
  )
  return nil unless result[:ok]
  top = result[:results].first
  return nil if top.nil? || top[:distance] > VECTOR_TIER_THRESHOLD
  top[:record].canonical_category
end
```

`VECTOR_TIER_THRESHOLD` is operator-tunable (default 0.35 cosine distance; below = match, above = fall through). The threshold is the substrate's calibration knob — too loose and the vector tier eats things the graph tier would resolve more precisely; too tight and the embedding investment is wasted. Bench-locked via `bin/mm-bench semantica_nearest`.

## What does NOT ship in PLAN_0_29_2

- **Upstream-authored `Semantica::Vector` facade.** Belongs to `vv-graph`'s v0.2.0 roadmap; this plan only consumes the pinned rev.
- **Consolidation subagent (`Mm::Semantica::Consolidator`).** Gap 2; PLAN_0_29_3. Embeddings drift as triples drift; the periodic re-embedding loop lands with the consolidator.
- **Episodic timeline (`Mm::Episodes::Recorder`).** Gap 3; PLAN_0_29_4.
- **Embeddings on models other than `Intention`.** `Product` + `ContextDocument` are natural candidates; deferred until operator demand surfaces specific queries. The DSL (`has_neighbors`) is one line per model; the substrate-side decision is what to embed + when, not how.
- **Local embedding model (no provider dependency).** Operators set `MM_EMBEDDING_MODEL` to a provider-backed model (OpenAI `text-embedding-3-small` default; Voyage / Cohere / etc. via the same env var). Local sentence-transformer-style embedding via WebGPU / llama.cpp is a separate sub-plan if operator demand surfaces — the substrate-as-offline-capable thesis applies but the embedding-model bring-up is its own project.
- **Hybrid retrieval (vector + BM25 + graph blend).** The cascade is sequential, not blended. Blended ranking is a more advanced retrieval surface; if the per-tier ordering proves wrong for a class of queries, the response is bench-driven threshold tuning before a re-architecture.
- **SPARQL UPDATE-style mutation through the vector facade.** `Semantica::Vector` is read + embed only; mutation rides through AR + `has_neighbors`'s normal write path.
- **Operator chrome for embedding inspection.** A `/sme/semantica/embeddings` viewer is plausible follow-up if operators ask "why did Tier 0a not match this?"; not in scope.
- **Cross-machine embedding cache coherence.** Same boundary PLAN_0_29_1 named: per-substrate-process / per-SQLite-file. Multi-substrate is V0.28.x cross-machine sync.

## What this plan DOES NOT claim

- **Not "MM authors the Vector facade."** That's upstream's v0.2.0 work; MM consumes the pinned rev.
- **Not "vector ANN replaces the graph or fuzzy tiers."** Tier 0a is *first* in the cascade because it's cheapest at the catalog's scale + has the best recall-vs-precision tradeoff for natural-language inputs; the other tiers stay because they catch what embeddings miss (exact stems, structured graph paths, novel categories).
- **Not "embeddings remove the LLM dependency."** Embedding *generation* needs a provider (OpenAI / Voyage / Cohere / local model); embedding *retrieval* doesn't. The substrate-as-offline-capable thesis applies to retrieval (works against the cached vectors); the compile-time embedding pass is provider-bound.
- **Not "every model gets embeddings."** `Intention` is the first + only target in PLAN_0_29_2 because it's the cascade's anchor; other models join when operator queries justify it.
- **Not "the threshold is the substrate's permanent answer."** `VECTOR_TIER_THRESHOLD` is a calibration knob, not a constant; PLAN_0_29_3's consolidator will revisit the threshold against accumulated evidence.

- **Trigger for revisit**: Phase E's cascade re-order commit lands cleanly + `bin/mm-bench semantica_nearest` records a baseline. If recall@5 underperforms the fuzzy tier on the same fixture, the embedding model choice + threshold both get re-examined before declaring Gap 1 closed.
