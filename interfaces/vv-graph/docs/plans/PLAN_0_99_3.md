# PLAN_0_99_3 — Named-graph N-Quads with per-branch graph URIs

> Slice 3 of [PLAN_0_99_0](PLAN_0_99_0.md). SPARQL-side analog of
> [PLAN_0_99_2](PLAN_0_99_2.md)'s fts filter.

## Answer to the framing question

**How does a SPARQL consumer ask "show me only main's triples"?**
By wrapping their pattern in `GRAPH <urn:mm:branch:main> { … }`. The
N-Quads format already supports this — every quad's 4th term is its
named graph. graph:extract switches that term from per-file to
per-branch under MM_INDEX_BRANCHES.

## The shape change in derived.nq

**Before (per-file named graphs):**

```nquads
<urn:mm:plan:PLAN_0_95_1> <https://magenticmarket.ai/plan#kind> "slice" <urn:mm:plan:PLAN_0_95_1> .
<urn:mm:research:OpenHuman> <https://magenticmarket.ai/research#kind> "research" <urn:mm:research:OpenHuman> .
```

**After (per-branch named graphs, when MM_INDEX_BRANCHES is set):**

```nquads
<urn:mm:plan:PLAN_0_95_1> <https://magenticmarket.ai/plan#kind> "slice" <urn:mm:branch:main> .
<urn:mm:plan:PLAN_0_95_1> <https://magenticmarket.ai/plan#kind> "slice" <urn:mm:branch:feature-x> .
<urn:mm:research:OpenHuman> <https://magenticmarket.ai/research#kind> "research" <urn:mm:branch:main> .
```

Same subject, same predicate, same object — different named graphs.
This is exactly the RDF semantics for "the same logical entity has
different views per branch."

## SPARQL consumer pattern

```sparql
# Triples about PLAN_0_95_1 on main:
SELECT ?p ?o WHERE {
  GRAPH <urn:mm:branch:main> {
    <urn:mm:plan:PLAN_0_95_1> ?p ?o .
  }
}

# Compare main vs feature-x for the same subject:
SELECT ?p ?main_o ?feature_o WHERE {
  GRAPH <urn:mm:branch:main>      { <urn:mm:plan:PLAN_0_95_1> ?p ?main_o }
  GRAPH <urn:mm:branch:feature-x> { <urn:mm:plan:PLAN_0_95_1> ?p ?feature_o }
  FILTER (?main_o != ?feature_o)
}

# List all branches indexed:
SELECT DISTINCT ?branch WHERE {
  GRAPH ?branch { ?s ?p ?o }
  FILTER STRSTARTS(STR(?branch), "urn:mm:branch:")
}
```

## Files touched

1. **`server/lib/tasks/graph.rake`** — graph:extract gains branch
   awareness. When MM_INDEX_BRANCHES is set, iterate branches via
   `enumerate_index_branches` (helper from slice 1); read content via
   `branch_read_blob` (also slice 1); emit each quad with
   `<urn:mm:branch:<name>>` as the 4th term. Embedded turtle blocks
   get wrapped in a `# from <rel> [branch=<name>]` comment header
   in the same file (embedded.ttl) so the downstream loader (when
   parsing) can route blocks to per-branch named graphs.

2. **Helper `branch_graph_uri(branch)`** — single source of truth
   for the `<urn:mm:branch:X>` URI shape. Used here + later by S4/S5.

## What's NOT in this slice

- **vv-planning branch column.** Slice 4 (PLAN_0_99_4). vv-planning's
  AR schema and the named-graph SPARQL projection are orthogonal —
  vv-planning is the operational AR view, named graphs are the
  read-side query layer.
- **Stale-branch GC.** Slice 5. Today, extract appends a branch's
  triples each time; if a branch is deleted, its triples linger.
- **Loading into sqlite-sparql.** The downstream consumer (Docker
  KG server) loads `derived.nq` via `rdf_insert_many` or similar.
  That code path doesn't need to change — N-Quads' 4th term is
  already the named graph; the loader honours it.

## Drift / rollback signals

- Embedded.ttl losing branch context (no `# from <rel> [branch=X]`
  header) → branch dimension dropped.
- A SPARQL consumer running `SELECT * WHERE { ?s ?p ?o }` (no GRAPH
  filter) gets cross-branch interleaved triples and is confused
  → document the GRAPH-required pattern in CLAUDE.md or a
  cross-branch principle doc.

## Exit criteria (slice "done")

- All success_criteria pass.
- A smoke session: MM_INDEX_BRANCHES=main rake graph:extract produces
  derived.nq with every line ending in `<urn:mm:branch:main> .`
  (verified via `tail -5 tmp/graph/derived.nq | awk` or similar).
- Without MM_INDEX_BRANCHES, the same task produces today's per-file
  4th term (no behaviour change).
