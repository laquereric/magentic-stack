# PLAN 0.4.18 — Iframe Interaction Model (3 Approaches)

## Problem

Rendered content (MCP UI components, slide previews) runs in a sandboxed iframe. The iframe has its own document, its own CSS, its own Stimulus — fully isolated. But user interactions inside the iframe (hover, click, type, select) need to reach the parent application's models (Context, Intention, Actor, ChatChannel).

The iframe can't directly access parent JS, parent ActionCable, or parent AR models. Every interaction must cross the `postMessage` boundary.

## Current Iframe Uses

| Surface | URL | Interactions Needed |
|---------|-----|---------------------|
| Slide preview | `/scenarios/:id/slides/:id/preview` | Click region → highlight, inspect element |
| MCP UI component render | `/render/dispatch` (SS mode in iframe) | Click → navigate, hover → tooltip, input → form submit |
| Turn screenshots | Selenium captures the preview URL | None (static capture) |
| Figma capture | `generate_figma_design(interface_url:)` | None (static capture) |

## Interaction Types

| Event | In Iframe | Needs to Become | In Parent |
|-------|-----------|-----------------|-----------|
| mouseover | Element highlight | Intention(action: "inspect") | AI modal shows element info |
| click | Element selected | Intention(action: "click", target: selector) | Parent navigates or creates Context |
| type | Input value | Context(publisher: "human", payload: text) | Chat message or form submission |
| select | Dropdown/checkbox | Context update | State change in slide region |
| scroll | Viewport position | (optional) viewport tracking | |

## The postMessage Contract

```
Iframe → Parent:
  { type: "mm:interaction", action: "click", target: ".card--main", props: {...}, origin: "preview" }

Parent → Iframe:
  { type: "mm:command", action: "highlight", target: ".card--main" }
  { type: "mm:command", action: "setState", target: ".todo-checkbox", state: "checked" }
```

## Approach 1: Stimulus Bridge Controller (Parent + Child Pair)

**Concept:** Two paired Stimulus controllers — one in the parent (`iframe-bridge`), one in the iframe (`bridge-child`). The child captures DOM events, serializes them, sends via `postMessage`. The parent receives them, creates AR records (Intention/Context), and can send commands back.

```
Parent document                              Iframe document
──────────────                               ───────────────

iframe-bridge controller                     bridge-child controller
  │                                            │
  ├── connect()                                ├── connect()
  │   └── addEventListener("message")          │   └── addEventListener("click")
  │                                            │   └── addEventListener("mouseover")
  │                                            │   └── addEventListener("input")
  │                                            │
  ├── received(event)                          ├── handleClick(e)
  │   ├── validate origin                      │   └── parent.postMessage({
  │   ├── create Intention                     │       type: "mm:interaction",
  │   ├── broadcast to ChatChannel             │       action: "click",
  │   └── update UI (highlight panel)          │       target: e.target.className,
  │                                            │       text: e.target.textContent
  │                                            │     })
  ├── sendCommand(action, target)              │
  │   └── iframe.postMessage({                 ├── receiveCommand(event)
  │       type: "mm:command", ...              │   ├── highlight element
  │     })                                     │   └── set state
```

**Files:**
- `app/javascript/controllers/iframe_bridge_controller.js` — parent side
- `public/js/bridge-child.js` — injected into iframe pages (preview.html.erb)
- Event → Intention/Context mapping in the parent controller

**Pros:** Reusable Stimulus pattern, clean separation, works with any iframe content
**Cons:** Two JS files to maintain, child script must be injected into every iframe page

## Approach 2: MessageBus Service Object (Centralized Event Router)

**Concept:** A single `MessageBus` JS class handles all iframe communication. Registered handlers map interaction types to application actions. The bus sits in the parent and dispatches to ChatChannel, AR models, or UI updates.

```
Parent:
  const bus = new MessageBus()
  bus.on("click", (data) => chatChannel.send({ text: `Clicked ${data.target}` }))
  bus.on("inspect", (data) => aiModal.showElementInfo(data))
  bus.on("input", (data) => createContext("human", data.text))

Iframe:
  // Minimal: just postMessage on events
  document.addEventListener("click", (e) => {
    parent.postMessage({ type: "mm:interaction", action: "click", ... }, "*")
  })
```

**MessageBus class:**
```javascript
class MessageBus {
  constructor() {
    this.handlers = new Map()
    window.addEventListener("message", (e) => this.dispatch(e))
  }

  on(action, handler) { this.handlers.set(action, handler) }

  dispatch(event) {
    if (event.data?.type !== "mm:interaction") return
    const handler = this.handlers.get(event.data.action)
    if (handler) handler(event.data)
  }

  sendToFrame(iframe, command) {
    iframe.contentWindow.postMessage({ type: "mm:command", ...command }, "*")
  }
}
```

**AR integration:**
```ruby
# When MessageBus creates a Context via fetch:
POST /interactions
{ session_id: "demo", action: "click", target: ".card--main", publisher: "human" }

# InteractionsController creates Intention + Context
```

**Files:**
- `public/js/message-bus.js` — parent MessageBus
- `public/js/bridge-child.js` — iframe event capture (same as A1)
- `app/controllers/interactions_controller.rb` — HTTP endpoint for AR records
- Route: `POST /interactions`

**Pros:** Centralized, extensible (add handlers without changing iframe code), clean API
**Cons:** Global singleton, not Stimulus-native, separate from existing controller pattern

## Approach 3: Custom Element (`<mm-frame>`) with Built-in Bridge

**Concept:** A Web Component `<mm-frame>` wraps `<iframe>` and handles all bridge logic internally. The custom element exposes events and methods. Parent code listens to custom events. The iframe child script is injected automatically.

```html
<!-- In parent -->
<mm-frame src="/scenarios/.../preview"
          data-session="demo"
          data-on-click="handleFrameClick"
          data-on-inspect="handleFrameInspect">
</mm-frame>
```

```javascript
class MmFrame extends HTMLElement {
  connectedCallback() {
    this.iframe = document.createElement("iframe")
    this.iframe.src = this.getAttribute("src")
    this.iframe.sandbox = "allow-scripts allow-same-origin"
    this.appendChild(this.iframe)

    // Inject child bridge script after load
    this.iframe.onload = () => this.injectBridge()

    // Listen for messages from child
    window.addEventListener("message", (e) => {
      if (e.source !== this.iframe.contentWindow) return
      if (e.data?.type !== "mm:interaction") return
      this.dispatchEvent(new CustomEvent("mm:" + e.data.action, { detail: e.data }))
    })
  }

  injectBridge() {
    const script = this.iframe.contentDocument.createElement("script")
    script.src = "/js/bridge-child.js"
    this.iframe.contentDocument.head.appendChild(script)
  }

  sendCommand(action, target, data = {}) {
    this.iframe.contentWindow.postMessage({ type: "mm:command", action, target, ...data }, "*")
  }

  highlight(selector) { this.sendCommand("highlight", selector) }
  setState(selector, state) { this.sendCommand("setState", selector, { state }) }
}

customElements.define("mm-frame", MmFrame)
```

**Parent usage with Stimulus:**
```javascript
// In any Stimulus controller:
this.element.querySelector("mm-frame").addEventListener("mm:click", (e) => {
  this.chatChannel.send({ text: `Inspected: ${e.detail.target}` })
})
```

**Files:**
- `public/js/mm-frame.js` — Web Component
- `public/js/bridge-child.js` — iframe event capture (auto-injected)
- No server changes needed (events dispatch to existing controllers)

**Pros:** Self-contained, reusable as `<mm-frame>`, auto-injects bridge, standard Web Component API, works with or without Stimulus
**Cons:** Web Components are less familiar in Rails ecosystem, injection requires same-origin

## Comparison

| Aspect | A1: Stimulus Pair | A2: MessageBus | A3: Custom Element |
|--------|------------------|----------------|-------------------|
| Pattern | Stimulus controllers | Global JS class | Web Component |
| Reusability | Per-iframe instance | Singleton | Per-element |
| Event handling | Stimulus actions | `bus.on()` handlers | Custom DOM events |
| AR integration | Stimulus → fetch | MessageBus → fetch | Custom event → fetch |
| Iframe injection | Manual script tag | Manual script tag | Auto-injected |
| Works with Stimulus | Native | Alongside | Alongside |
| Encapsulation | Controller scope | Global | Shadow DOM possible |

## The Child Script (Shared by All Approaches)

```javascript
// bridge-child.js — runs inside every iframe
(function() {
  const TRACKED_EVENTS = ["click", "mouseover", "mouseout", "input", "change", "focus", "blur"]

  TRACKED_EVENTS.forEach(type => {
    document.addEventListener(type, (e) => {
      const target = e.target.closest("[class]")
      if (!target) return

      parent.postMessage({
        type: "mm:interaction",
        action: type,
        target: target.className.split(" ")[0],
        selector: buildSelector(target),
        text: target.textContent?.slice(0, 100),
        value: target.value,
        rect: target.getBoundingClientRect()
      }, "*")
    }, { passive: true })
  })

  // Receive commands from parent
  window.addEventListener("message", (e) => {
    if (e.data?.type !== "mm:command") return
    const el = document.querySelector(e.data.target)
    if (!el) return

    switch (e.data.action) {
      case "highlight":
        el.style.outline = "2px solid #58a6ff"
        el.style.outlineOffset = "2px"
        setTimeout(() => { el.style.outline = ""; el.style.outlineOffset = "" }, 2000)
        break
      case "setState":
        el.dataset.state = e.data.state
        break
    }
  })

  function buildSelector(el) {
    if (el.id) return `#${el.id}`
    const cls = el.className.split(" ").filter(c => c && !c.startsWith("--"))[0]
    return cls ? `.${cls}` : el.tagName.toLowerCase()
  }
})()
```

## Recommendation

**Approach 3 (`<mm-frame>` Custom Element)** — most encapsulated. The bridge logic is invisible to the rest of the app. Parent code uses standard DOM events (`mm:click`, `mm:inspect`). Auto-injects the child script. Works with Stimulus controllers that already manage the page. No global state.

Approach 1 is the fallback if Web Components feel too alien in the Rails stack.
