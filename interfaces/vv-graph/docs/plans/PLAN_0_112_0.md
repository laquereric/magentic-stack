# PLAN_0_112_0 — Persistence bridge: AR projections → cross-process visibility

> Closes the architectural seam PLAN_0_111_0's end-to-end demo
> surfaced — in-process AR Oxigraph Store invisible to
> bin/mm-graph and the Docker KG.

## The architectural reality

`vendor/sqlite-sparql/src/store.rs` is explicit:

> Process-wide Oxigraph in-memory store. One `Store` for the
> lifetime of the process, lazily initialised on first use and
> shared by every SQLite connection on every thread.

That is: every process has its own Store. The Rails server,
`bin/mm-graph`, and the Docker KG container are three separate
processes. AR-projected triples written by Storable's after_save
hooks live in the Rails process's Store and nowhere else.

```
┌────────────────────────┐    ┌────────────────────────┐    ┌────────────────────────┐
│ Rails server process   │    │ bin/mm-graph process   │    │ Docker KG container    │
│ ┌────────────────────┐ │    │ ┌────────────────────┐ │    │ ┌────────────────────┐ │
│ │ in-mem Oxigraph    │ │    │ │ in-mem Oxigraph    │ │    │ │ in-mem Oxigraph    │ │
│ │ ← AR Storable      │ │    │ │ ← --ttl flags      │ │    │ │ ← tmp/graph/*.nq   │ │
│ └────────────────────┘ │    │ └────────────────────┘ │    │ └────────────────────┘ │
└────────────────────────┘    └────────────────────────┘    └────────────────────────┘
        invisible to ──────────────────  invisible to ──────────────────  invisible to
```

## The bridge: tmp/graph/ar/

```
                                          ┌────────────────┐
                                          │ tmp/graph/ar/  │
                                          │  vv_planning_  │
                                          │   plans.nq     │
                                          │  vv_agent_     │
                                          │   tasks.nq     │
                                          │  vv_process_   │
                                          │   runs.nq      │
                                          └───────▲────────┘
                                                  │
                                          rake graph:ar:export
                                                  │
                                          ┌───────┴────────┐
                                          │ Rails AR layer │
                                          └────────────────┘
                                                  │
                              ┌───────────────────┼───────────────────┐
                              ▼                   ▼                   ▼
                  bin/mm-graph auto-loads   graph:server:reload   anyone else
                                            picks up + reboots   (mm-next-probe
                                            Docker KG            via bin/mm-graph)
```

## What lands

1. **`server/lib/tasks/graph.rake`** — new `graph:ar:export`
   task. Iterates `ActiveRecord::Base.descendants` for
   Storable-bearing models, writes one N-Quads file per model
   into `tmp/graph/ar/`.
2. **`bin/mm-graph`** — auto-loads `tmp/graph/ar/*.nq` when the
   directory exists. AR projections become visible to every
   external SPARQL query.
3. **`graph:server:reload`** — gains a step (run `graph:ar:export`
   before `graph:extract`) so the Docker KG sees AR projections
   on reload.
4. **`docs/recipes/mm-graph-queries.md`** — Q7/Q8/Q10 drop their
   "no-KG bash fallback" subsections; the SPARQL path is finally
   the canonical answer.

## What this plan does NOT do

- **It does not eliminate the per-process Oxigraph
  separation.** A real fix would be a `sqlite-sparql` Rust-side
  rewrite to use a persistent backend. Out of scope; the
  workaround is good enough for the substrate's current load.
- **It does not add real-time sync.** Operators run
  `graph:ar:export` explicitly (or wait for
  `graph:server:reload`). A follow-on adds a file watcher or an
  `after_save` debounced exporter if low latency matters.
- **It does not add a `Storable.dump_triples_to(io)` helper.**
  The first iteration writes the export logic inline in
  graph.rake — keeps the surface change small. A follow-on
  promotes the helper to vv-graph when a second consumer wants
  it.
- **It does not handle cross-graph subject-IRI collisions.**
  Same subject (e.g. `urn:mm:plan:PLAN_0_107_0`) may project via
  AR (this slice) AND via `graph:extract` from frontmatter (the
  existing path). RDF set-merge semantics keep this safe; a
  follow-on slice adds source-attribution predicates if
  disambiguation becomes operationally load-bearing.

## Acceptance signal

```bash
cd server
bin/rails graph:ar:export
ls -la ../tmp/graph/ar/
# → vv_planning_plans.nq    (~31 rows × 11 predicates)
#   vv_agent_tasks.nq       (empty today; 0 rows)
#   vv_process_runs.nq      (empty today; 0 rows)
```

```bash
bin/mm-graph --format table -q '
PREFIX plan: <https://magenticmarket.ai/plan#>
SELECT ?status (COUNT(?p) AS ?n) WHERE {
  GRAPH <urn:mm:graph:plans> { ?p a plan:Plan ; plan:status ?status }
} GROUP BY ?status'
# → done   30
#   draft   1
```

Compare against:
```bash
cd server && bin/rails runner 'puts Vv::Planning::Plan.group(:status).count'
# → {"done"=>30, "draft"=>1}
```

Match.

## Risks

| Risk | Mitigation |
|---|---|
| Stale tmp/graph/ar/ between runs | Operator-driven trigger today; follow-on adds watch mode |
| Cross-graph subject collisions | RDF set-merge keeps it safe; document in graph.rake; follow-on adds source predicates if needed |
| Per-process separation remains | Out of scope; this is a workaround, not a fix to sqlite-sparql |
| Rails boot in reload pipeline | Already slow; acceptable; document |
| Disk balloon on large substrates | Per-table files + rewrite-on-export keeps growth bounded |
