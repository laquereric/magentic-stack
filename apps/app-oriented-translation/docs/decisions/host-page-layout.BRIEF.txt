Design how a HOST PAGE lays out an OSI Level 8 Profile 9 ACIA tree. Deliver a markdown design document. Design only, no implementation.

== The decision this follows from ==
An operator decision has been made and is not open for revisiting: LAYOUT STAYS THE HOST PAGE'S JOB. The component library (vv-html-components) styles components IN PLACE and will not become a layout engine. Your job is to design what the host page must do instead, and what contract it needs in order to do it.

== The situation, precisely ==
Three things exist today:

1. A deterministic renderer emits semantic HTML from an ACIA tree. Per node it
   emits a tag chosen from semanticRole (landmark->main, list->ul,
   article->article, button->button, timeline->ol, ...) carrying data-ux-node-cid,
   data-ux-node-id, data-ux-component-kind, data-ux-acia-digest,
   data-ux-token-digest, data-ux-content-role and aria-label. Nesting mirrors the
   tree. It emits NO layout: no grid, no columns, no widths.

2. vv-html-components is a static, dependency-free light-DOM library added with
   ONE script include. It selects on data-ux-component-kind and styles nodes in
   place. It reads slt.layoutKind and slt.layoutArity ZERO times today. It never
   alters data-ux-* attributes and never reparents nodes.

3. The ACIA tree ALREADY CARRIES THE LAYOUT INTENT and nobody consumes it:
     LAYOUT_KINDS  = stack | inline | grid | split | overlay | timeline | table
     LAYOUT_ARITY  = one | two | three | many
   plus a responsiveSignature field, currently always "default".

The concrete failure this causes: the StewardshipTranslation Board is five
columns, expressed correctly as a grid PanelFrame containing five PanelFrames.
Rendered today it is five panels STACKED VERTICALLY — a long scroll, not a board.
The structural claim holds semantically and is invisible visually.

== What you must design ==

1. THE CONTRACT. What exactly does the host page need from the ACIA tree and
   from the rendered markup in order to lay it out? Be concrete: is
   slt.layoutKind + layoutArity sufficient, or is something missing? The host can
   read any data-ux-* attribute and can read the embedded ACIA JSON-LD document
   the page already carries. It must NOT require the renderer to change.

2. WHO APPLIES IT. The host page is a Rails view, or a static page, or the CPCP
   FRONT pod. Options include: a stylesheet the host ships that keys off
   data-ux-* and layout attributes; a host-side CSS generation step; a
   convention the page author follows by hand. Recommend one and say what it
   costs the author.

3. THE MISSING SIGNAL. layoutKind lives in slt, which is in the ACIA document,
   NOT in the emitted HTML — the renderer does not emit layoutKind as an
   attribute. So a stylesheet alone cannot see it. State plainly how the host
   gets it: read the embedded JSON-LD, or propose a NUMBERED Profile 9 change
   emitting a layout attribute, with blast radius. Do not assume the change is
   approved.

4. RESPONSIVE. responsiveSignature exists and is always "default". Five columns
   cannot survive a narrow viewport. What should it carry, and what happens to a
   grid PanelFrame at phone width? A board that becomes an unreadable squeeze is
   worse than one that becomes a stack — say what the correct degradation is and
   why.

5. THE DEGRADATION FLOOR. With NO host stylesheet and NO component library, the
   page must remain readable. With the library but no host layout, it must remain
   readable. Neither may throw. State what each of those three states looks like
   for the board specifically.

6. WHO OWNS WHAT. One paragraph a developer can act on: renderer owns X,
   component library owns Y, host page owns Z. The current confusion is that
   layout intent is authored in the tree and consumed by nobody.

== Constraints ==
- The renderer's per-node markup does not change. It is digest-covered and
  conformance-pinned.
- The component library does not become a layout engine. That is the decision.
- No external CSS framework, no build step, no runtime network.
- Do not invent ACIA component kinds. The closed nineteen are fixed.
- Existing pages must not break.

== Deliver ==
1. The contract, stated as something a developer implements.
2. Recommended mechanism, with what it costs the page author.
3. How the host obtains layoutKind, including any numbered Profile 9 proposal
   with blast radius, NOT assumed approved.
4. Responsive behaviour and the correct narrow-viewport degradation.
5. The three degradation states for the board.
6. The ownership paragraph.
7. Anything you believe should NOT be built, and why.
