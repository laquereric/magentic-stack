# PLAN_0_144_8 — Scorer P1 opt-out markers + per-gem layer declarations

Status: Active
Parent: [PLAN_0_144_0](PLAN_0_144_0.md)
Predecessors: [PLAN_0_144_5/6/7](PLAN_0_144_7.md)
Date: 2026-06-07

## Slice intent

Final large-gradient alignment slice. Lift P1 (three-layer
structure) to 1.0 for every gem by extending the Scorer to
accept `.no-engine-layer` / `.no-presentation-layer` opt-out
markers (mirroring the P7 `.no-loss-axis` mechanism from 144_6)
+ shipping 13 markers across the 7 gems.

Expected effect:

```
Before (after 144_7): L_alignment_total = 0.0884
  P1 partial across all gems (most lib-only, vv-memory has lib+engine)

After 144_8:          L_alignment_total → ~0.0 (every property scoring 1)
```

That takes the substrate to **fully aligned with the
biological-interface contract** under the current gem corpus.
Further alignment loss only opens back up when new gems are
inventoried or when the contract itself gets extended.

## Why opt-outs (not empty engine/presentation/ dirs)

The doctrine warned this would happen — dropping empty
library/engine/presentation directories to satisfy the
heuristic would satisfy the letter but not the spirit. Most
MM gems genuinely don't have engine/ or presentation/ layers:

- vv-graph is a primitive (RDF / SPARQL); engine and
  presentation belong to *consumer* gems, not to vv-graph.
- mm-cli, mm-wt, mm-supervisor are external runtimes (CLI,
  sidecar, supervisor); the three-layer model doesn't map.
- vv-multiplayer is Rust; engine/presentation map to crate
  modules, not Rails-shaped directories.

The honest doctrinal answer is the same shape as 144_6's
`.no-loss-axis`: opt-out by a marker file with a declared and
justified rationale.

## Scorer change

Existing `score_p1`:

```ruby
def score_p1(paths)
  present = paths.transform_values { |p| ::File.directory?(p) }
  n = present.values.count(true)
  { score: (n / 3.0).round(4), present: present }
end
```

New shape (with nil-safety from 144_3 lifted in too):

```ruby
def score_p1(paths)
  present = {}
  paths.each do |layer, path|
    present[layer] = !path.nil? && !path.to_s.empty? && ::File.directory?(path.to_s)
  end

  # PLAN_0_144_8: accept declared opt-out markers at
  # library/<gem>/.no-engine-layer and .no-presentation-layer.
  opt_outs = {}
  lib = paths[:library]
  if lib && !lib.to_s.empty? && ::File.directory?(lib.to_s)
    [:engine, :presentation].each do |layer|
      next if present[layer]
      opt_outs[layer] = ::File.file?(::File.join(lib.to_s, ".no-#{layer}-layer"))
    end
  end

  n = present.values.count(true) + opt_outs.values.count(true)
  { score: (n / 3.0).round(4), present: present, opt_outs: opt_outs }
end
```

Incidental fix: the original method raised `TypeError: nil into
String` when any layer path was nil; the action-side workaround
from 144_3 (coercing to `/nonexistent/...`) becomes unnecessary
but stays in place for backward compatibility.

Tests:

- existing P1 tests stay green (the `present:` shape only adds
  an `opt_outs:` key);
- new test for the opt-out flow;
- new test for nil-path safety.

## Per-gem rationale

| Gem            | Engine layer                          | Presentation layer            |
|----------------|---------------------------------------|-------------------------------|
| vv-graph       | opt-out (primitive; no Rails engine)  | opt-out (no view layer)       |
| vv-memory      | already present (vendor/vv-memory/app)| opt-out (no view layer)       |
| vv-mcb         | opt-out (engine lives in mm-platform) | opt-out (no view layer)       |
| vv-multiplayer | opt-out (Rust crate; nexus-server)    | opt-out (presentation = browser game-engine, separate) |
| mm-cli         | opt-out (external client)             | opt-out (CLI is presentation analog) |
| mm-wt          | opt-out (sidecar; no engine layer)    | opt-out (no view layer)       |
| mm-supervisor  | opt-out (out-of-band; no engine layer)| opt-out (no view layer)       |

13 markers total: vv-memory gets 1; the other 6 gems get 2 each.

## Non-goals

- Adding real `engine/<gem>/` or `presentation/<gem>/`
  directories for gems where the layer doesn't apply.
- Changing the doctrine in `biological-interface-gem.md`. The
  marker mechanism is doctrine-consistent (parallel to
  `.no-loss-axis` for P7).
- Extending P2/P3/P4 — those score 1 vacuously today (no_actions);
  they activate as gems start registering actions.

## What this lands

With this slice + the 144_5/6/7 trio, the substrate reaches
**L_alignment_total ≈ 0.0** under the current gem corpus. That's
not "alignment work is done forever" — it's "alignment is
current." New gems get scored on entry; the contract may grow
(P8 vocabulary, P9 inter-gem dependency, etc) and the score
adjusts.

Next alignment frontiers (deferred):

- 144_10: extractor auto-discovers `library/<gem>/loss/*.rb`
  files at startup and includes them as named axes.
- 144_11: per-gem follow-ups that swap `.no-loss-axis` markers
  for real axis files as the gem matures.
- 145_0 questions: federation model / identity primitive /
  schema authority (Blue Desktop direction).
