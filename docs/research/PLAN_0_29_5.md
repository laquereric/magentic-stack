# PLAN 0.29.5 — Unwind `Mm::Triples` shim into direct `Semantica::Sparql` calls (PLAN_0_29_1 B.3 follow-up)

> *V0.29.x cleanup. PLAN_0_29_1 Phase B.2 (commit `74df79e`) shipped the irreversible cutover from the legacy `Triple` AR model to the sqlite-sparql / Oxigraph store via `Semantica::Storable`, with a substrate-side `Mm::Triples` query shim (`server/packs/platform/app/services/mm/triples.rb`, 231 LOC) mimicking the old `Triple.where/about/objects_for/...` class-method API. The shim was an explicit interim — it kept the B.2 commit small by avoiding a 15-file SPARQL port. PLAN_0_29_5 closes the loop: each `Mm::Triples.*` call site graduates to a direct `Semantica::Sparql.select(query, graph: "urn:mm:graph:bhphoto")` call, file by file, as it's touched for other reasons OR in one focused sweep — operator's call. When every call site has migrated, the shim file deletes; `Mm::Triples` ceases to exist.*

## The strategic frame

Three observations:

1. **The shim was pragmatic, not principled.** Keeping a Triple-like API alive made the B.2 commit smaller (one-token renames in 15 files vs. per-file SPARQL ports). It also hid the SPARQL boundary behind an MM-substrate-internal abstraction — which is OK for an interim but slightly violates the doctrine that MM should consume `Semantica::Sparql` directly.

2. **Direct calls are clearer + faster.** Each shim invocation pays a small overhead (Relation object construction, lazy SPARQL build, TripleStub wrapping for the result rows). A direct `Sparql.select` with a hand-written query is one round-trip + one envelope. For hot paths (`OntologyResolver.seed!`'s category enumeration, `WikiCompiler.compile_all`'s per-Intention triple walk), the overhead matters.

3. **The shim's surface is small enough to inline.** Only seven entry points (`where`, `about`, `objects_for`, `subjects_where`, `table_exists?`, `count`, and the `Relation` chain). Each call site uses one of them and threads it through `pluck` / `first` / `each`. Translation is mechanical; the only judgment per site is "which SPARQL shape best expresses the query."

The strategic move: **collapse the shim by direct inlining**, one caller at a time. No new abstraction; each call site owns its SPARQL query string and the result-row unwrapping it needs.

## Why not just leave the shim

The shim works and the substrate ships. So why bother?

- **Two boundaries are worse than one.** Today `Sparql.select` is the upstream's contract; `Mm::Triples` is a substrate-side wrapper around it. Bugs surface in two places; envelope drift has to be tracked in two places. The drift-detection contract in `vendor/vv-graph/CONSUMER_REQUIREMENT_MM.md` names `Sparql.*` as the surface MM consumes — the shim is an internal layer that complicates that story.
- **The shim hides query shape.** `Mm::Triples.where(predicate: "schema:category").distinct.pluck(:object)` reads like AR but compiles to `SELECT ?o FROM <urn:mm:graph:bhphoto> WHERE { ?s <schema:category> ?o }` — different perf characteristics, different optimization opportunities. Inline SPARQL makes the actual query reviewable.
- **TripleStub's N-Triples unwrapping is implicit substrate policy.** Each caller already knows whether it wants the IRI-wrapped form or the bare value; inline calls make the unwrap explicit at each call site.

Counter-argument: the shim isolates the legacy-graph-name → URI mapping (`"bhphoto"` → `"urn:mm:graph:bhphoto"`). When inlined, every caller has to spell the URI explicitly. Mitigation: a module-level constant `Mm::Bhphoto::GRAPH_IRI = "urn:mm:graph:bhphoto"` referenced at call sites.

## What's in the shim today

| Surface | Used by | LOC saved on inline |
|---|---|---|
| `.where(...)` → `.pluck(:subject)` | folder_query (×2), search_node, wiki_compiler (×2), ontology_resolver.seed!, compare_products, query_first_responder (×2), category_focus (×2) | ~3 lines/call |
| `.where(...)` → `.distinct.pluck(:object)` | wiki_compiler, ontology_resolver.seed! | ~3 lines/call |
| `.about(uri)` → iterated `.each` | folder_query, search_node, wiki_compiler, product_projector, product_focus, wiki_builder | ~5 lines/call |
| `.objects_for(s, p)` → `.first` / `.include?` | folder_query (×3) | ~2 lines/call |
| `.table_exists?` | ontology_resolver.seed! (guard) | trivial — drop the guard |
| `.count` | update_product_feed (×2), get_analytics | ~2 lines/call |

Plus the shim itself: `server/packs/platform/app/services/mm/triples.rb` (231 LOC).

## What ships in PLAN_0_29_5

### Phase A — Add `Mm::Bhphoto::GRAPH_IRI` constant

One-line module declaration somewhere appropriate (likely `server/packs/partner_bhphoto/lib/mm/bhphoto.rb` or inline at the top of each call site that needs it). Justifies the shim removal — every call site that previously got the graph-name-to-URI translation for free now references one named constant.

### Phase B — Inline call sites, file by file

Each of the ~15 files independently migratable. Suggested order (hot paths first):

1. `server/packs/platform/app/services/ontology_resolver.rb` — `seed!` was already gated by `Mm::Triples.table_exists?` (which returns false in B.2+); the entire Triple-seeding branch can be DELETED. The graph-traversal Tier 0 added in Phase C already handles category resolution from live SPARQL.
2. `server/packs/platform/app/services/wiki_compiler.rb` — three call sites, all read-heavy. Replace with `Sparql.select` queries scoped to `Mm::Bhphoto::GRAPH_IRI`.
3. `server/packs/partner_bhphoto/app/services/folder_query.rb` — six call sites; the heaviest single file. The `triples.each do |t|` loop in `product_data` benefits most from inline SPARQL (one query returning the row set vs. the shim's Relation+TripleStub overhead per row).
4. `server/packs/partner_bhphoto/app/services/search_node.rb`, `clause_node.rb`, `compare_node.rb`, `folder_graph.rb` — the bhphoto query DAG; do these in one pass.
5. `server/packs/platform/app/models/intention/{product_focus,category_focus}.rb`, `materialized/wiki_builder.rb` — read paths on intention compile.
6. `server/packs/platform/app/services/mm/product_projector.rb`, `mm/tools/{compare_products,update_product_feed,get_analytics}.rb` — the MM-tool wrappers.
7. `server/packs/marketplace/app/services/query_first_responder.rb` — closes the list.

Each file's commit is independent. The shim stays alive until the last file migrates.

### Phase C — Delete the shim

Once every call site uses `Sparql.select` directly:

- Delete `server/packs/platform/app/services/mm/triples.rb`.
- Update `server/spec/architecture/semantica_substrate_audit_spec.rb`: the assertion "`Mm::Triples` shim is loaded" flips to `expect { Mm::Triples }.to raise_error(NameError)`.
- `CONSUMER_REQUIREMENT_MM.md`'s drift-signal section already names `Sparql.*` — no change needed there.

## Out of scope for PLAN_0_29_5

- **Performance optimization beyond inlining.** Caching, prepared SPARQL, bulk-loading patterns — separate plan, driven by `bin/mm-bench` evidence.
- **Replacing `Mm::Bhphoto::GRAPH_IRI` with named-graph multi-partition.** The substrate runs one operator's data in one graph; multi-graph emerges only when operator demand surfaces.
- **Schema-level changes (new predicates, ontology updates).** Inline porting preserves existing predicate names + IRIs.
- **Touching `Semantica::Storable`'s write path.** B.2 already wired writes through Storable; B.3 only affects reads.

## Risks specific to PLAN_0_29_5

| Risk | Likelihood | Mitigation |
|---|---|---|
| Inlined SPARQL query has a subtle shape difference from what the shim emitted, returning a different row set | medium | Each file's port runs the existing spec suite for that file before the commit. The shim's tests + the substrate's integration specs catch most divergence. |
| Object-type semantics differ — caller expected bare string but inlined query returns `<wrapped>` form | medium | Each call site explicitly unwraps via a small `unwrap_iri` / `unwrap_literal` helper (~3 LOC, copy-paste per site is fine; cohesion isn't important here). |
| Forgotten call site — `Mm::Triples` constant lingers after "phase C" deletion attempt | low | A `grep -rn "Mm::Triples"` step gates the shim-deletion commit. The architecture spec's `raise_error(NameError)` assertion fails loudly if the shim deletes prematurely. |
| File-by-file porting drags on for months, leaves the shim half-alive indefinitely | low | If the substrate hasn't fully migrated by the time PLAN_0_29_2 (vector ANN) ships, the operator picks a sweep date + does the remaining files in one focused session. |

## Exit criteria

PLAN_0_29_5 is shippable when:

- `grep -rn "Mm::Triples"` returns zero hits across `server/packs/` and `server/spec/` (excluding the `architecture/semantica_substrate_audit_spec.rb` line that asserts its absence).
- `server/packs/platform/app/services/mm/triples.rb` is deleted.
- The B.3 audit assertion (`expect { Mm::Triples }.to raise_error(NameError)`) replaces the "shim is loaded" assertion in the audit spec.
- Full spec suite green with the shim gone.

## Order of operations

This plan is deliberately **operator-paced**, not date-paced:

- Phase A (constant declaration) ships in one tiny commit; or inlined into the first file's commit.
- Phase B's file ports happen file-by-file as developers touch each file for other reasons (drive-by porting) OR in one focused sweep session. Either pattern works.
- Phase C (shim deletion + audit flip) is the final commit; gated by Phase B completion.

## V0.29.5 status

- **Form**: substrate-side cleanup follow-up to PLAN_0_29_1 Phase B.2; no upstream dependency.
- **Action**: drive-by porting OR focused sweep; ~15 files; ~200 LOC removed when the shim deletes.
- **Risk if ignored**: low. The shim is functionally correct; the substrate ships fine without B.3. Cost of deferral is two-boundaries-instead-of-one — substrate-side polish, not blocking.
- **Trigger for revisit**: when an MM developer hits the shim's overhead in a benchmark, OR when V0.29.x → V0.30.x trigger fires (the upstream gem reaches v1.0 + the substrate audits its consumption surface).
