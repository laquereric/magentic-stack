# PLAN 0.15.2 — AI Developer: `skills` + `topology` Direct Edit

> *Engineering-altitude implementation plan with experience-altitude implications.* Second non-Designer Role to ship end-to-end; first Role with two DE surfaces. Follows the completion checklist defined in PLAN 0.15.0, extended for the two-surface case. Citations: PLAN 0.15.0 (horizontal arc + completion checklist), PLAN 0.15.1 (Data Engineer template — single-surface analog), PLAN 0.13.94 (ai_developer profile + chrome bindings), PLAN 0.13.95 (`skills` + `topology` DE surface declaration), PLAN 0.13.91 (Skill registry + Skill::Loader), PLAN 0.13.94 PR 4 (orchestration_bus.yml topology), PLAN 0.14.17 (trust gradient — ai_developer default Watch), PLAN 0.14.21 (state-vs-artifact triad — both surfaces write state), `docs/architecture/Vocabulary.md`.

## Purpose

PLAN 0.15.1 proved the horizontal arc with a single-surface Role (Data Engineer / `schema_docs`). PLAN 0.15.2 extends it to a **two-surface Role** — AI Developer — whose `roles.yml` declares both `skills` (`.skill.md` files) and `topology` (`config/orchestration_bus.yml`) as Direct Edit surfaces. This is the first time the substrate ships two Stage subtypes for one Role in the same plan.

Reasons AI Developer goes second:

1. **Both surfaces are state-shaped** per the Thariq triad (PLAN 0.14.21). `.skill.md` is markdown with YAML frontmatter; topology is YAML. Both round-trip cleanly through git. No interface-vs-artifact ambiguity.
2. **Both surfaces already validate at write time** under the legacy whole-file DE path (TopologyController checks YAML parses; Skill::Loader's `InvalidFrontmatter` raises on bad frontmatter). PLAN 0.15.2's job is to wrap those existing validators in typed Stages + predicates, not invent new validation infrastructure.
3. **Both surfaces are small.** Five `.skill.md` files exist today; `orchestration_bus.yml` declares four channels. Blast radius is bounded.
4. **The recursive proposer hazard is real but already mitigated.** AI Developer's DE writes `.skill.md` files that the Companion *reads* as system-prompt body. A skill-edit that breaks the proposer's own runbook is a self-corrupting hazard. The mitigation already exists: per PLAN 0.14.17 `Sme::Profile#role_default("ai_developer")` returns `Harness::TrustMode::WATCH` — every commit requires human review by default. The plan adds one predicate (`skill_frontmatter_valid` runs `Skill::Loader.parse_yaml` + validation) so the proposer can never write a frontmatter that Skill::Loader will refuse on the next reload.

When 0.15.2 ships, AI Developer passes the same nine-line completion checklist Designer + Data Engineer pass. The substrate has shipped three Roles complete; the horizontal arc is genuinely past its proof-of-concept moment.

## What ships

Phased the same way as 0.15.1: A → D.

### Phase A — substrate primitives

**Two typed Stage subtypes.**

`Harness::Stage::SkillEdit` — represents one wholesale `.skill.md` write. SCHEMA:

```ruby
SCHEMA = {
  skill_path:    String,                                       # e.g. "packs/marketplace/skills/foo.skill.md"
  skill_name:    String,                                       # frontmatter "name" field
  role:          String,                                       # frontmatter "role" field
  mode:          ->(v) { %w[preturn turn postturn both].include?(v.to_s) },
  frontmatter:   Hash,                                         # full parsed frontmatter (round-trips through YAML)
  body:          String,                                       # markdown body, no frontmatter delimiters
  intent_text:   String,
  sme_role:      String,
  target_files:  ->(v) { v.is_a?(Array) && v.all? { |f| f.is_a?(String) } && v.any? }
}
SYMBOL_PAYLOAD_FIELDS = %i[mode]
```

`Harness::Stage::TopologyEdit` — represents one channel-shaped change to `orchestration_bus.yml`. SCHEMA:

```ruby
SCHEMA = {
  change_type:    ->(v) { %i[add update remove].include?(v.to_sym) },  # what kind of channel change
  channel_name:   String,                                              # e.g. "harness.skill"
  purpose:        ->(v) { v.nil? || v.is_a?(String) },                 # nil only for :remove
  publishers:     ->(v) { v.is_a?(Array) && v.all? { |p| p.is_a?(String) } },
  subscribers:    ->(v) { v.is_a?(Array) && v.all? { |s| s.is_a?(String) } },
  intent_text:    String,
  sme_role:       String,
  target_files:   ->(v) { v.is_a?(Array) && v.all? { |f| f.is_a?(String) } && v.any? }
}
SYMBOL_PAYLOAD_FIELDS = %i[change_type]
```

The TopologyEdit is **channel-scoped**, not whole-file: each Stage touches one channel by name. This matches Designer's "wholesale at a stable anchor" pattern (the channel name is the anchor) and avoids the diff-merge complexity of partial line edits.

**DSL package `Harness::AiDeveloper::*`.**

- `Harness::AiDeveloper::SkillRouter` — analog of `DataEngineer::DocRouter`. Routes a `(pack, skill_name)` pair to a file path under `packs/<pack>/skills/<skill_name>.skill.md`. Refuses traversal. The allowed slug pattern matches `Skill::Loader`'s `KNOWN_ROLES` and snake-case names. `SKILLS_ROOTS` is an Array because skills can live in multiple packs.
- `Harness::AiDeveloper::SkillIndex` — analog of `DataEngineer::SectionIndex`. Walks every `.skill.md` via the same globs `SkillRegistry::SKILL_GLOBS` uses, returns the list of (skill_name, path) pairs. mtime-keyed cache; `invalidate(skill_path)` after a write.
- `Harness::AiDeveloper::TopologyParser` — wraps `YAML.safe_load(File.read("config/orchestration_bus.yml"))` and exposes `channel_names`, `channel(name)`, `exists?(channel_name)`. Same mtime-keyed cache pattern.
- `Harness::AiDeveloper::TopologyWriter` — channel-scoped insert / update / remove. Reads the current YAML, merges the Stage's change, writes back. Preserves comment lines via a line-level re-emit pass.
- `Harness::AiDeveloper::Predicates` — six predicates:

| Predicate | What it checks | Failure example |
|---|---|---|
| `skill_frontmatter_valid` | Stage's frontmatter passes `Skill::Loader.validate!` shape (`name` and `role` present; role in `KNOWN_ROLES`; mode in `GlobalRoute::MODES`; `harness_components` subset of allowed). | proposing role: "marketer" (not in KNOWN_ROLES) |
| `skill_body_well_formed` | Body is non-empty, balanced code fences, no `<script>` tags, under MAX_BODY_LINES (200). | unclosed ` ``` ` block |
| `topology_yaml_parses` | After applying the Stage's change, the resulting YAML still parses as `{channels: [...]}`. | dropping the top-level `channels:` key |
| `topology_channel_resolves` | For `:update` and `:remove`, the named channel exists in the current topology. For `:add`, the named channel does NOT already exist. | adding "harness.turn" when it's already there |
| `topology_no_orphan_subscribers` | Every subscriber named in `publishers` / `subscribers` resolves to a class name reachable via `safe_constantize`. (Best-effort — a recently-renamed class fails this honestly.) | subscriber `Harness::Ghost` does not exist |
| `routed_to_correct_surface` | `target_files` matches the routed path under `SkillRouter` (for SkillEdit) or `config/orchestration_bus.yml` (for TopologyEdit). | skill_path pointing outside packs/*/skills/ |

`Predicates.bundle_for(stage)` dispatches on stage class: SkillEdit gets the four skill predicates + `routed_to_correct_surface`; TopologyEdit gets the three topology predicates + `routed_to_correct_surface`.

**Altitude vocabulary extension.** Five new keys added to `Altitude::ENGINEERING.canonical_requirements_vocabulary`:

```
skill_frontmatter_valid
skill_body_well_formed
topology_yaml_parses
topology_channel_resolves
topology_no_orphan_subscribers
```

`routed_to_correct_surface` is **already in the vocab** (it's the generalised form `routed_to_correct_file` from Designer's bundle — re-used directly). No vocab key needs to be added for routing.

**Wait — vocabulary correction.** `routed_to_correct_file` (Designer) and `routed_to_schema_dir` (Data Engineer) are surface-specific. AI Developer's two surfaces would want their own keys: `routed_to_skill_path` and `routed_to_topology_file`. The cleaner pattern is *one predicate key per surface*. Adds two more keys. Architect's-no #7 is happy.

Final five vocabulary additions:

```
skill_frontmatter_valid
skill_body_well_formed
topology_yaml_parses
topology_channel_resolves
topology_no_orphan_subscribers
```

Plus the surface-specific routing keys are absorbed under a single new key:

```

```

…which the routing predicate uses, dispatching by stage class internally. Six new vocabulary keys total.

### Phase B — Companion proposers + skills

**Two Companion proposers.**

`Harness::Companion::AiDeveloperSkillEditProposer` — one tool: `propose_skill_edit`. Input fields: `skill_path`, `skill_name`, `role`, `mode`, `frontmatter` (object), `body` (string), `intent_recap`, `reasoning`. Returns a typed `Stage::SkillEdit` via `ProposalResponse`.

`Harness::Companion::AiDeveloperTopologyEditProposer` — one tool: `propose_topology_edit`. Input fields: `change_type` (enum), `channel_name`, `purpose`, `publishers` (array), `subscribers` (array), `intent_recap`, `reasoning`. Returns a typed `Stage::TopologyEdit` via `ProposalResponse`.

Both proposers mirror `DesignerCssEditProposer` line-for-line: skill body load, system prompt assembly, Anthropic call, tool-call validation, Stage construction. The Anthropic stub gains two more canned tool calls (selected by tool name) so both proposers' specs run deterministically.

**Two skill runbooks.**

`packs/marketplace/skills/ai_developer_skill_propose.skill.md` — runbook for the Companion's skill-edit flow. Steps: recognise the intent (frontmatter change vs body change), identify the target `.skill.md` path, compose the full frontmatter + body, call `propose_skill_edit`. Includes the recursive-proposer caveat: *never propose to modify a skill named `ai_developer_*` without explicit Data Engineer review*, surfaced in the chrome card.

`packs/marketplace/skills/ai_developer_topology_propose.skill.md` — runbook for the channel-shaped topology change. Steps: recognise the intent (add / update / remove channel), look up existing channels via `TopologyParser`, compose `publishers`/`subscribers` as fully-qualified class names, call `propose_topology_edit`.

### Phase C — Reconciler hookup + chrome card

**`Harness::DirectEdit::Reconciler.reconcile!`** — already accepts `surface:` as a parameter; no change. The new surfaces are `skills` and `topology`.

**`Harness::SkillsController#commit_proposal`** — new action mirroring `SchemaDocsController#commit_proposal`. Accepts the typed `Stage::SkillEdit` payload, runs `AiDeveloper::Predicates.bundle_for(stage)` through `Harness::Turn.reconcile`, writes via a SkillWriter helper on `:committed`.

**`Harness::TopologyController#commit_proposal`** — same shape, for `Stage::TopologyEdit`. Writes via `TopologyWriter`.

**Two new routes:**
```
POST /harness/skills/commit_proposal     → skills#commit_proposal
POST /harness/topology/commit_proposal   → topology#commit_proposal
```

**Chrome partials** mounted under `conversation_pane` (AI Developer's `chrome.preturn_draft_buffer: true` per `roles.yml` — so the partials *can* mount in either place; we mount in conversation_pane for consistency with Data Engineer's pattern):

- `app/views/regions/conversation_pane/_skill_edit_proposal.html.erb`
- `app/views/regions/conversation_pane/_topology_edit_proposal.html.erb`

Both follow the same shape as `_schema_doc_proposal.html.erb`: header, intent recap, pre-rendered proposed state, mode dial, Accept/Edit/Reject actions.

**Trust gradient calibration.** `Sme::Profile#mode_for(role: "ai_developer", stage_type: ...)` already returns `:watch` by default (PLAN 0.14.17). No new code; the spec verifies the calibration.

## What does not ship

- **`Stage::SkillEdit` for cross-pack moves.** A `.skill.md` file that needs to relocate between packs is two operations (write new + delete old). 0.15.2 ships single-location wholesale-write only.
- **`Stage::TopologyEdit` for channel renames.** A rename is a remove + add. 0.15.2 ships the three primitive change_types only.
- **Preview rendering for topology changes.** A topology change has non-local effects (publishers / subscribers wire together at boot). The substrate ships *predicates*, not a *runtime simulator*. Predicates catch the wire-time errors; runtime regressions stay caught by the broader test suite as today.
- **Skill registry hot-reload on commit.** `SkillRegistry.reset!` should be called after a `SkillEdit` commits so the next proposer call sees the new skill. The action lands in `SkillWriter`; no separate machinery.

## Open questions resolved by this plan

- **Recursive proposer hazard.** *Resolved.* Three layers of defense: (1) ai_developer's default trust mode is Watch (PLAN 0.14.17); (2) `skill_frontmatter_valid` runs `Skill::Loader.validate!` so a SkillEdit that produces unloadable frontmatter never commits; (3) the runbook explicitly tells the Companion to refuse self-edits unsolicited. The substrate's discipline + a Watch-by-default trust mode + a frontmatter predicate together make this hazard tractable without a runtime sandbox.
- **Topology preview rendering.** *Resolved.* No preview shipped; predicates are the protection. `topology_no_orphan_subscribers` (best-effort constantize) catches the most common error class. Runtime regressions are caught by the broader test suite, not by a topology-specific simulator.

## Risk register

| Risk | Likelihood | Mitigation |
|---|---|---|
| `TopologyWriter`'s comment-preserving re-emit drops formatting | medium | Phase A spec tests round-trip preservation; if it breaks, fall back to YAML re-emit without comments (acceptable since commits are auditable in git) |
| `SkillWriter` and `SkillRegistry.reset!` race in production multi-process | low | Reset happens in the writing process; other processes pick up changes on their next request (existing dev-mode behaviour) |
| Companion proposes invalid `composed_routes` (not in `GlobalRoute`) | medium | `skill_frontmatter_valid` already runs `Skill::Loader.validate!` which enforces this; the Stage refuses at the predicate gate |
| Two Stages from the same proposer race-commit | low | Single-writer assumption holds in dev; production deferred to 0.16.x |
| AI Developer's chrome has `preturn_draft_buffer: true` but we mount in conversation_pane — inconsistent with Data Engineer | low | acceptable; documented in tutorial; per-Role chrome is a roles.yml concern, not 0.15.2's |
