## The rule

CPCP keeps HTTP 200 only for an intentionally completed RPC method
whose result is a **domain decision**. Endpoint failures use HTTP
error statuses. JSON-RPC 2.0 is transport-agnostic and prescribes no
HTTP mapping; the mapping is CPCP policy. The body stays a never-raise
envelope. Status describes the transport/outcome of the exchange.

Vault already does `json:` + `status:` (row 49). That is a
compatibility baseline, not a copy-verbatim for BACK: vault is REST
and a flat `{ok, reason, because}`; BACK is nested
`Envelope.fail` (`ok` + `error.{reason, because}`). Do not flatten
Envelope this turn.

## Grounding is HTTP 200; 422 is a different event

Manus listed a grounding refusal both as 200-domain-outcome and under
422-semantic-rejection. Those cannot both be right for one event.

**Grounding is HTTP 200.** In this tree it is the method completing:
`cpcp_adapter` raises `KnownRefusal grounding_refused` after evaluating
the domain payload against SHACL. Reclassifying that as 422 would say
the request was unprocessable *as HTTP content*, which erases that the
method ran and decided, and makes `failure_layer` vestigial for the
common refusal. One SHACL event, one status.

**422** is reserved for a well-formed JSON-RPC request whose *request
document* (params as a CPCP instruction shape) fails SHACL **before**
Dispatcher invokes the method. BACK has no such gate today.
`RequestBody` only distinguishes `empty_body` / `unparseable_json`
(those become 400). A later request-shape gate may emit 422. It must
not relabel `grounding_refused`.

## `failure_layer` (designed, not decided)

Wire enum, on `error` next to `reason`/`because`, required under
`dual-v1` for `{ok:false}`:

`domain` | `http_auth` | `http_request` | `infrastructure`

It sits on `error` so `BackCpcpClient`'s re-wrap (which keeps `error`
and drops unknown top-level keys) does not lose it.

**Owner call, not filled:** whether every admission/refusal is a domain
decision or an endpoint-auth failure. `authorization_denied` stays
HTTP 200 as a completed method result. Its `failure_layer` in the
table is the sentinel `owner`, which is **never a wire value**. Methods
that produce that reason stay on `legacy-all-200` until the owner
fills the layer. The mapper must not guess `domain` or `http_auth`.

HTTP 401 (missing/invalid credentials, `WWW-Authenticate`) and 403
(authenticated-but-not-permitted at the HTTP/resource layer) are
distinct classes. They have no live BACK producer today
(`RpcController` skips CSRF; auth belongs in projected handlers).
They are not a back-door decision of the admission row.

method results.

## 503 is not a general retry signal

`Retry-After` only when the recovery window is known **and** replay is
safe (idempotency key present, or the method is idempotent). A
non-idempotent POST without a durable key is never retried on 503.
This tree has already duplicated a blob by retrying. `retryable` is
not a wire field in v1; it is mapping-table and log guidance.
Status must not be read as permission to replay.

404 refusals are `Cache-Control: no-store`. POST is not cacheable
without explicit freshness metadata.
