# Gap 112: the unreachable-GRAPH plant was stale, not the code

`plant_projection_unreachable.rb` asserted Immediate recorded
`graph_unreachable` and `sparql_parse_error`. After gap 69 it recorded
`outbox_schema_check_failed` twice. The other assertions still passed
(`emit-envelope`, `schedule-error`, `n=2`).

## Diagnosis, confirmed

Gap 69 made `Immediate#schedule` refuse on `schema_status` **before**
GRAPH. The harness had no ActiveRecord connection, so
`schema_status` rescued to `:check_failed` and
`refuse_undurable!` wrote `outbox_schema_check_failed`. SPARQL was
never called. `:error` is the right return; the **reason** is the
outbox reason, not the GRAPH reason. The code is right. The plant
was asking the no-outbox fixture for a GRAPH refusal.

`outbox_schema_check_failed` rather than `outbox_not_installed`
because `:check_failed` is "the lookup raised" and `:missing` is "AR
is up and the table is not there". No connection is the first, not
the second.

## What the plant does now

Three faults, three reasons. A SPARQL stub of `graph_unreachable`
must not be recorded when the outbox is missing.

| fixture | `schema_status` | recorded reason |
|---|---|---|
| no AR connection | `:check_failed` | `outbox_schema_check_failed` |
| AR up, no table | `:missing` | `outbox_not_installed` |
| `ensure_schema!` (specs only) | `:available` | `graph_unreachable` / `sparql_parse_error` |

Did not change Immediate. Did not collapse the reasons into "any
refusal". Did not `create_table` at runtime in production code;
`ensure_schema!` remains specs-only, which this plant is.

`check_outbox_schema.py` now fails if the plant drops one of the
three named cases.
