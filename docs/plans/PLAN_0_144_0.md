# PLAN_0_144_0 — gem alignment: L_alignment + biological-interface conformance

Status: Direction
Family: 144 (new top-level; sibling to 140 / 141 / 142 / 143)
Date: 2026-06-07

## Headline

Grade every MM gem against the seven-property biological-
interface contract from
[`../architecture/principles/biological-interface-gem.md`](../architecture/principles/biological-interface-gem.md).
Project the per-gem score into a graph (`urn:mm:alignment`),
expose it via MCB, feed it into the per-Turn L extractor, and
drive the existing gems toward conformance.

## Why now

Three threads converged:

1. **JSON-LD + SHACL on the wire** — the operator's framing
   makes the contract enforceable; before that, biological
   structure was an aspirational convention without bite.
2. **The graph is the meeting point** — PLAN_0_140 + 142 + 143
   already write to per-gem named graphs. The substrate now has
   the read surface that makes "gem state is graph-visible" a
   testable property, not a wish.
3. **The substrate is dependable** — PLAN_0_141 makes restart +
   health + drain MCB-driven. SUPERDEV AI can run the alignment
   loop continuously without operator handholding.

The seven properties are the *targeted shape*; L_alignment is
the *gradient*; this family is the *gradient descent*.

## Architecture

```
  Biological-interface contract       ← docs/architecture/principles/biological-interface-gem.md (doctrine)
        │
        │ specifies 7 properties (P1..P7)
        v
  Harness::Alignment::Scorer          ← per-gem scoring (144_1)
        │
        │ emits triples into urn:mm:alignment
        v
  Harness::Alignment::GraphProjection ← alignment Turtle (144_2)
        │
        v
  alignment_score MCB action          ← read surface (144_3)
        │
        v
  Per-Turn L axis alignment_delta     ← contribution to L (144_4)
        │
        v
  Per-gem alignment slices            ← drive each existing gem (144_5 .. _N)
        │
        v
  L_alignment_total → 0               ← the gradient-descent target
```

## Slices (sketch)

- **144_1 — Scorer + per-property heuristics.** Pure stateless
  `Harness::Alignment::Scorer.score(gem:)` returning the seven
  per-property scores + composite. Heuristics enumerated below.
- **144_2 — urn:mm:alignment graph.** GraphProjection +
  alignment_score MCB action; same shape as routing /
  hypersource projections (Bindable now, INSERT DATA later).
- **144_3 — gem inventory.** A SPARQL-queryable list of MM's
  gems (canonical IRI + library/engine/presentation paths +
  version) so the scorer has a corpus to iterate.
- **144_4 — L axis: alignment_delta_per_gem.** Per-Turn
  contribution: did this Turn make any gem's alignment score
  go down? Drives the closed loop.
- **144_5 .. _N — per-gem alignment work.** Each underperforming
  gem gets a slice; aim is one slice per missing property until
  the gem hits L_alignment = 0.

### Per-property heuristics (v0.1 for 144_1)

Not perfect; good enough to drive the first round of alignment.

- **P1 three-layer:** `1` if `library/<gem>/`, `engine/<gem>/`,
  `presentation/<gem>/` all exist on disk, else fraction present.
- **P2 JSON-LD wire:** `1` if every action's source contains an
  `@context` reference *and* envelope shape, else fraction.
  v0.1 grep; v0.2 actually call each action with a probe input.
- **P3 SHACL shapes:** `1` if every action has both an
  `<action>.input.ttl` and `<action>.output.ttl` in
  `library/<gem>/shapes/`, else fraction.
- **P4 ≤ 7 actions:** count actions whose source files match
  the gem's path prefix; `1` if ≤ 7, else `7 / count`.
- **P5 graph projection:** `1` if the gem has at least one
  module under `library/<gem>/graph_projection.rb` *or* its
  actions reference `Vv::Graph::Sparql.execute`, else `0`.
- **P6 pattern exec:** `1` if a `bin/<gem>-pattern` (or
  similar stamped binary) exists, else `0`.
- **P7 L axis:** `1` if any file under `library/<gem>/loss/` OR
  if `library/<gem>/.no-loss-axis` marker file (declared opt-out)
  exists, else `0`.

## L_alignment per the doctrine

Reproduced for convenience:

```
L_alignment(G)   = mean over P1..P7 of (1.0 - score_P_i(G))
L_alignment_tot  = mean over G of L_alignment(G)
```

Zero is perfect alignment; higher is more drift.

The alignment work is a long ladder; each slice is small and
focused on one (gem, property) pair.

## Non-goals

- Not retro-rewriting any gem. Alignment work is *additive*: add
  the missing pack, add the SHACL shape, add the pattern
  executable. No semantic changes to working gems.
- Not enforcing alignment at boot. v0.1 reports; gating happens
  later if the operator decides drift is a real problem.
- Not a one-shot rewrite. Alignment is continuous; this family
  ships the *grader*, then the gradient descent runs over many
  sittings.
- Not a quality metric for the work *inside* a gem. L_alignment
  measures whether the gem *shape* is biological-interface-
  conformant. Code quality is the 133 family's lint /
  complexity axes.

## What this unblocks

- A coherent narrative for AndrewT + future joiners: "this is
  what an MM gem looks like." The 7-property doctrine + the
  L_alignment grader is the spec.
- Cross-language gems: once a candidate runtime (Rust, Python)
  can produce a P1–P7 score of 0, it's a first-class MM
  participant.
- HA + DR (141_5 + 141_7): graph-replication is the canonical
  state-transport because every aligned gem's state is in the
  graph.
- LLM agents introspecting unfamiliar gems via SHACL +
  pattern exec + graph queries — no human-curated docs needed.

## Open questions

1. **Score weighting.** Equal-weight mean per property today.
   Empirically some properties (P5 graph projection, P3 SHACL)
   may matter more than others. Adjust after the first round
   of measurements.
2. **Continuous re-grading cadence.** Per-Turn vs per-day vs
   per-commit? First instinct: per-Turn for the
   alignment_delta_per_gem axis (so the 133 L extractor sees
   it); per-day for the substrate-wide L_alignment_total
   report.
3. **Gem inventory canonical source.** Bundler `Gemfile.lock` +
   `Cargo.lock` + manual list vs auto-discovery via
   `Vv::Pattern::Registry`. First instinct: auto-discovery if
   the registry already enumerates them; else manual list in
   `docs/architecture/gem-inventory.ttl`.
