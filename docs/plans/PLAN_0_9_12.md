# PLAN 0.9.12 — Implementation Optimization

## Review: 0.9.0–0.9.11

Twelve plans were written. One was implemented (0.9.3 — triple store). The rest describe overlapping systems that, if built independently, would create redundant infrastructure. This plan identifies the shared primitives, eliminates duplication, and defines a minimal implementation path.

## Redundancy Map

Several plans describe the same thing from different angles:

| Concept | Appears In | Redundancy |
|---------|-----------|------------|
| Product query with constraints | 0.9.0 (FolderConstraint), 0.9.3 (FolderQuery), 0.9.9 (BNF grammar), 0.9.10 (SearchExplorer) | **4 implementations of the same query** |
| Product comparison | 0.9.0 (FolderComparison), 0.9.1 (graph edges), 0.9.9 (CompareGrammar), 0.9.10 (CompareNode) | **4 implementations of comparison** |
| TCO calculation | Already exists (TcoCalculator), 0.9.0 (folder TCO), 0.9.9 (TcoGrammar), 0.9.10 (TcoNode) | **Calculator exists — others are wrappers** |
| Model routing | 0.9.4 (LlmRouter), 0.9.5 (MmModels + ModelInteraction) | **0.9.5 supersedes 0.9.4** |
| Task classification | 0.9.6 (approach analysis), 0.9.8 (READMEs) | **0.9.8 is documentation of 0.9.6** |
| Knowledge compilation | 0.9.1 (graph edges), 0.9.7 (wiki pages) | **Different formats, same goal** |

## Shared Primitives

Everything converges on five primitives:

### 1. The Grammar (single query language)

Plans 0.9.0, 0.9.3, 0.9.9, 0.9.10, 0.9.11 all need to express product queries. One grammar serves all:

```
price:<400 ink:tank duty:>800
```

This grammar is the **single input format** for:
- Chat (`/search price:<400 ink:tank`)
- Explorer controls (dropdown changes update the grammar string)
- API (`POST /api/v1/search` with grammar body)
- LLM tool calls (LLM generates grammar, not JSON)
- Folder creation (grammar string stored as the folder's query)
- SHACL generation (grammar → SHACL shape is a deterministic transform)

**Build once:** `GrammarParser` with `SearchGrammar`, `CompareGrammar`, `TcoGrammar`.

### 2. The Triple Store (single data layer)

Plan 0.9.3 is implemented. Plans 0.9.0 (folders), 0.9.1 (graph edges), 0.9.2 (vectors) all add data to it. Don't build separate tables — everything is triples:

- Product specs → triples (done: `ProductTripler`)
- Folder constraints → triples (done: `FolderGraph`)
- Graph relationships (COMPETES_WITH, COMPLEMENTS) → triples with `COMPUTED`/`INFERRED` provenance
- Vector embeddings → **separate** (sqlite-vec virtual table — can't be a triple)

**Already built.** Extend, don't rebuild.

### 3. The Grammar Node (single output format)

Plan 0.9.10 defines AST nodes that emit JSON-LD + SHACL + MCP UI. This is the **single output pipeline** — every query result flows through it:

```
Grammar string → Parser → AST → {
  to_context_record()  → triple store (audit)
  to_shacl()           → folder query (execution)
  to_mcp_ui()          → component (rendering)
  to_grammar_string()  → round-trip (display)
}
```

**Build once:** `GrammarNode` base class, concrete nodes per grammar.

### 4. The SearchExplorer Component (single UI)

Plans 0.9.10 (chat) and 0.9.11 (no-chat) describe two layouts for the same component. Don't build two components — build one `SearchExplorerComponent` that renders in either region:

- In chat: compact, embedded in message bubble
- In main: full-width, standalone page
- Same Stimulus controller, same WAMP calls, same grammar parser

**Build once:** `SearchExplorerComponent` with a `mode` prop (`chat` | `page`).

### 5. The Model Router (single LLM decision point)

Plans 0.9.4 and 0.9.5 overlap. 0.9.5 supersedes 0.9.4 entirely. Don't build both.

- `MmModels` loads YAML configs from `vendor/mm-models/`
- `ModelInteraction` persists every call (replaces cache-based `ModelScorecard`)
- `LlmRouter` scores and selects based on `ModelInteraction` history + YAML defaults
- `LlmService` instruments calls and records to `ModelInteraction`

**Build 0.9.5 only.** Skip 0.9.4.

## What NOT to Build

| Plan | Proposed | Skip | Why |
|------|----------|------|-----|
| 0.9.0 | SearchFolder, FolderProduct, FolderConstraint, FolderComparison tables | **Skip tables** | Folders are triples (0.9.3). Constraints are grammar strings. Comparisons are grammar results. No new tables needed. |
| 0.9.1 | ProductEdge table, ProductGraphBuilder | **Skip table** | Edges are triples with `COMPUTED`/`INFERRED` provenance. Use `Triple.assert!` with edge-type predicates. |
| 0.9.2 | EmbeddingService, VectorIndexer, SemanticSearch, HybridSearch | **Defer** | Vector search needs sqlite-vec extension. Implement after grammar search is working — grammar covers 80% of search needs without vectors. |
| 0.9.4 | LlmRouter, ModelScorecard (cache-based) | **Skip** | Superseded by 0.9.5 (MmModels, ModelInteraction). |
| 0.9.7 | Full wiki directory structure | **Defer** | Wiki is valuable but large. Start with product pages only, generated by rake task. Category/comparison/guide pages come later. |

## Implementation Order

### Phase 1: Grammar Parser (foundation)

Everything depends on the grammar. Build it first.

```
vendor/mm-models/tasks/*/grammars/  → BNF definitions
packs/platform/app/services/grammar_parser.rb  → dispatcher
packs/partner_bhphoto/app/services/search_grammar.rb
packs/partner_bhphoto/app/services/compare_grammar.rb
packs/partner_bhphoto/app/services/tco_grammar.rb
```

**Depends on:** nothing
**Enables:** everything else

### Phase 2: Grammar Nodes (AST → projections)

Each AST node emits ContextRecord + SHACL + MCP UI.

```
packs/platform/app/services/grammar_node.rb  → base class
packs/partner_bhphoto/app/services/search_node.rb
packs/partner_bhphoto/app/services/clause_node.rb
packs/partner_bhphoto/app/services/compare_node.rb
packs/partner_bhphoto/app/services/tco_node.rb
```

**Depends on:** Phase 1
**Enables:** chat integration, explorer, API

### Phase 3: SearchExplorer Component

One component, two modes.

```
packs/partner_bhphoto/app/view/components/search_explorer/
app/javascript/controllers/search_explorer_controller.js
app/view/styles/explorer.css
```

**Depends on:** Phase 2
**Enables:** interactive shopping (chat and no-chat)

### Phase 4: Graph Enrichment (triple store)

Add computed/inferred edges to existing triple store.

```
packs/partner_bhphoto/app/services/graph_enricher.rb
  → TCO_CHEAPER_THAN edges (COMPUTED)
  → COMPETES_WITH edges (COMPUTED — same category, similar price)
  → COMPLEMENTS edges (INFERRED — printer + scanner)
```

**Depends on:** existing triple store (0.9.3)
**Enables:** graph-aware search results

### Phase 5: Model Router (LLM optimization)

```
vendor/mm-models/ → YAML configs (tasks, providers, models, assignments)
db/migrate/*_create_model_interactions.rb
packs/platform/app/models/model_interaction.rb
packs/platform/app/services/mm_models.rb
packs/platform/app/services/llm_router.rb
packs/platform/app/services/llm_service.rb → add instrumentation
```

**Depends on:** nothing (independent track)
**Enables:** cost optimization, eval framework

### Phase 6: Wiki (product pages)

Start small — product pages only.

```
wiki/products/*.md → generated by rake task
wiki/index.md
wiki/SCHEMA.md
lib/tasks/wiki.rake
```

**Depends on:** triple store (for product data)
**Enables:** wiki-backed chat answers (cheaper, faster)

### Phase 7: Vector Search (deferred)

Only if grammar + graph search proves insufficient for discovery.

```
sqlite-vec extension
packs/partner_bhphoto/app/services/embedding_service.rb
packs/partner_bhphoto/app/services/vector_indexer.rb
```

**Depends on:** sqlite-vec availability, embedding model selection
**Enables:** "quiet printer for photos" (semantic, not keyword)

## Dependency Graph

```
Phase 1: Grammar Parser
    ↓
Phase 2: Grammar Nodes (AST → projections)
    ↓
Phase 3: SearchExplorer Component
    ↓
Phase 4: Graph Enrichment ← existing triple store (0.9.3)
    
Phase 5: Model Router (independent)

Phase 6: Wiki (after triple store)

Phase 7: Vector Search (deferred)
```

Phases 1–3 are the critical path. Phase 4 enriches results. Phase 5 is independent. Phases 6–7 are deferred.

## Migration Reduction

Plans 0.9.0–0.9.2 proposed 4 new migrations (search_folders, folder_products, folder_constraints, folder_comparisons, product_edges, product_vectors). With this optimization:

| Proposed Migration | Decision |
|-------------------|----------|
| `create_search_folders` | **Skip** — folders are triples |
| `create_folder_products` | **Skip** — membership is triples |
| `create_folder_constraints` | **Skip** — constraints are grammar strings in triples |
| `create_folder_comparisons` | **Skip** — comparisons are grammar results |
| `create_product_edges` | **Skip** — edges are triples with provenance |
| `create_product_vectors` | **Defer** — Phase 7 |
| `create_model_interactions` | **Keep** — Phase 5 |

**Result: 1 migration instead of 7.** The triple store (already built) absorbs everything except model interactions and vectors.
