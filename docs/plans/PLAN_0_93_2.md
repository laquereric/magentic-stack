# PLAN_0_93_2 — A fast path from slow Ruby to fast Rust (and faster browser WASM)

> *Research question: could a **shared SQLite/SPARQL instance**, a
> **shared filesystem**, and **[Rails Event Store](https://railseventstore.org/)**
> give the substrate a fast path — letting hot work migrate off slow Ruby
> onto fast Rust (`vendor/vv-multiplayer` / native workers over
> `vendor/sqlite-sparql`) and onto even-faster browser WASM (the local
> renderer)? The appeal is obvious: Ruby owns routing/auth/policy but is
> the slowest tier; Rust runs the tick loop and heavy SPARQL/inference;
> the browser, holding a local replica, answers reads with zero network
> round-trip. The instinct is "share one SQLite file across all three and
> skip serialization." This plan answers the question honestly — the
> answer is **a qualified yes**, but **not by the mechanism the question
> assumes**, because the RDF graph is not in the file. The fast path is
> real; its spine is RES, not the filesystem.*

## Answer to the research question

**Yes — but the shared *file* is not what shares the graph. The shared
*event log* is.** Three findings decide the shape:

| Mechanism | Shareable across processes via the file today? | Why |
|---|---|---|
| Ordinary SQLite tables | ✅ yes | Normal SQLite pages; WAL gives concurrent readers + one writer. |
| `sqlite-vec` vectors | ✅ yes | Stored as a vtab backed by real SQLite pages. |
| **RDF triples / SPARQL** (`sqlite-sparql`) | ❌ **no** | Oxigraph runs as **one in-memory store per process** (`sqlite-sparql` README §architecture); a persistent backend is **deferred**. Two processes opening the same file get **two independent graphs**. |

So "share the SQLite file and Rust sees Ruby's triples" **does not hold
today**. What *does* hold:

1. **The shared file is the fast lane for tables + vectors** (and, crucially, for the RES event log itself — see below) between **co-located** Ruby and Rust processes: same host, WAL mode, no wire, no JSON.
2. **RES is the shared truth for the graph.** Ruby (the governed writer) appends domain events; every tier **projects** those events into *its own* in-memory Oxigraph store. The log is shared (it's ordinary SQLite tables, file-shareable); the materialized graph is per-tier and rebuilt by replay. This is not a workaround — it is already implied by the in-memory store (a process restart must rebuild the graph from *somewhere*; RES is that somewhere).
3. **The browser is a *replica*, not a sharer.** A browser cannot mmap a host's SQLite file. It runs SQLite/Oxigraph in WASM over **OPFS**, subscribes to the RES stream over the [`PLAN_0_93_1`](PLAN_0_93_1.md) S2 transport, and replays into a local store. Strong consistency within the host (file + WAL); eventual consistency for the browser (replay).

```
   WRITES (governed, slow)                 READS / COMPUTE (fast → fastest)
   ┌─────────────────────┐
   │ RUBY (Rails)        │  append domain events
   │ routing·auth·policy │ ───────────────┐
   └─────────────────────┘                │
                                          ▼
                           ┌──────────────────────────────┐
                           │ Rails Event Store             │   ← shared truth
                           │ (event log = SQLite tables    │
                           │  in the shared file)          │
                           └───┬───────────────┬───────────┘
            same-host file     │               │   S2 transport (WS/SSE/ActionCable/WAMP)
            (WAL, no wire)     ▼               ▼
                    ┌──────────────────┐  ┌──────────────────────────┐
                    │ RUST worker      │  │ BROWSER WASM             │
                    │ tails log → own  │  │ replays log → own        │
                    │ Oxigraph + vec;  │  │ OPFS Oxigraph/SQLite;    │
                    │ hot SPARQL/OWL-RL│  │ local reads, 0 round-trip│
                    │ /SHACL/vector    │  │                          │
                    └──────────────────┘  └──────────────────────────┘
```

**The fast path, stated plainly:** Ruby stops *computing* SPARQL,
inference, SHACL, and vector search and instead *governs writes + appends
events*. The tier nearest the data answers the query — Rust for
server-side hot paths, browser WASM for the user-facing read path — each
over its own store, all fed by the one RES log.

## Why now

1. [`PLAN_0_93_1`](PLAN_0_93_1.md) already names RES as a transport
   carriage and frames "RES events projected into the frame schema." This
   plan extends that: RES is also the **state-sync** spine, not just a UI
   wire.
2. [`PLAN_0_3_0`](PLAN_0_3_0.md)'s "RUST feeds" already puts Nexus on
   `sqlite-sparql` + `sqlite-vec` via `rusqlite`
   ([`vendor/vv-multiplayer/CLAUDE.md`](../../vendor/vv-multiplayer/CLAUDE.md)).
   The Rust read/compute tier is partly built.
3. The in-memory-store constraint is a *current* fact, not a permanent
   one — naming it now decides whether we invest in the deferred
   persistent backend or lean on RES replay. Cheaper to choose before
   either tier hardens.

## The mechanism

### M1 — Write ownership is partitioned (no two writers)
SQLite is single-writer (WAL = many readers + one writer). The substrate
already partitions writes: governed domain state is written by **Ruby**;
ephemeral/spatial sim state is owned by **Rust** (Nexus), and identity is
**never** stored in `nexus-persist` — it is resolved from the substrate
([`vendor/vv-multiplayer/CLAUDE.md`](../../vendor/vv-multiplayer/CLAUDE.md)
boundary). The fast path keeps this: one writer per row-space; the log is
append-only (writer = whoever owns the aggregate).

### M2 — RES lives in the shared SQLite file
Store the RES event log as ordinary tables in the shared database. Then a
co-located Rust worker **tails new events by reading the same file** (WAL,
no wire, no JSON) and a browser **replays** them over the S2 transport.
The event log becomes the one durable, ordered source of truth all three
tiers agree on; the per-tier Oxigraph store is a **projection** of it.

### M3 — Projection, not sharing, of the graph
Each tier maintains its own in-memory Oxigraph store, kept current by
applying RES events (a triple-delta projection). This sidesteps the
in-memory-per-process limit entirely and gives each tier a graph at its
own locality and speed. Snapshots bound replay cost (M-spike below).

### M4 — The browser tier is OPFS-backed and replica-only
Browser WASM (Oxigraph-WASM and/or SQLite-WASM + `sqlite-vec`) holds a
**scoped** replica in OPFS, seeded by a snapshot + tail. It serves the
user-facing read path locally; it never writes authoritative state — user
intents go back through Ruby's governed write path
([`PLAN_0_93_1`](PLAN_0_93_1.md) S4 props are read-only).

## Scope — spikes (this is a research plan; each phase is a proof)

### S1 — RES-in-SQLite, Rust tail (the core bet)
Put RES tables in the shared file; a Rust worker tails appended events
from the same file and projects them into its Oxigraph store. **Prove:**
a triple Ruby writes (as an event) is queryable in the Rust tier within
one tail cycle, with no HTTP/JSON between them.

### S2 — Benchmark the fast path
Pick representative operations (a multi-hop SPARQL, an OWL-RL
materialization, a SHACL validate, a vector kNN). Measure three ways:
Ruby-direct (`vv-graph`) vs Rust-delegated vs browser-WASM-local.
**Prove:** the delegation is worth the projection cost for hot paths;
quantify the win and the staleness window.

### S3 — Snapshot + replay bound
Browser replay from genesis is O(history). Add periodic snapshots (a
serialized store state, e.g. N-Triples dump via `rdf_dump_ntriples` +
event cursor). **Prove:** a cold browser reaches current state in
snapshot-load + bounded tail, not full-history replay.

### S4 — Browser WASM feasibility (highest-risk spike)
Stand up the browser store. **Open question:** does `sqlite-sparql` (a
`sqlite-loadable-rs` `cdylib`) build for WASM and load into SQLite-WASM,
or do we use the **Oxigraph npm/WASM** build directly for the browser
tier? **Prove:** a browser can answer a SPARQL SELECT over an OPFS-backed
store seeded from a snapshot. If the extension won't load in WASM, the
fallback (Oxigraph-WASM directly) still satisfies the fast path —
document which.

### S5 — Persistent-backend decision
Evaluate the deferred Oxigraph persistent (RocksDB) backend in
`sqlite-sparql`. If it lands, co-located Ruby+Rust could share the graph
*through the file* (M3 becomes optional for the host tier). **Decide:**
RES-replay-only (cheaper, ships now) vs persistent-backend (true file
sharing, more upstream work). RES-replay is the default; persistence is an
optimization, not a prerequisite.

## Out of scope
- **Replacing Ruby's governance role.** Ruby keeps routing, auth, scope,
  policy, and the write gate. "Slow" is fine for governance; only *hot
  compute* migrates.
- **Cross-host shared SQLite.** SQLite over NFS/network filesystems is
  unsafe (locking). The file-sharing fast path is **same-host only**;
  cross-host is RES-over-the-wire, never a shared mount.
- **The WebMCP / Prompt-API consumer work** — that is
  [`PLAN_0_93_0`](PLAN_0_93_0.md); it rides this substrate, doesn't define
  it.
- **Rewriting Oxigraph or the extension's surface** — we consume
  `sqlite-sparql`'s functions as-is (`sparql_query`, `rdf_insert_many`,
  `rdf_owl_rl_materialise`, SHACL validate, the `rdf_triples` vtab).
- **A new component vocabulary or transport schema** — inherited from
  PLAN_0_3_0 / PLAN_0_93_1 unchanged.

## Risks

| Risk | Mitigation |
|---|---|
| **The premise's trap:** assuming the shared file shares the graph. It does not — Oxigraph is in-memory, per-process. | This plan's whole design (RES as the shared truth, M3 projection) is built on that fact; S1 proves the real mechanism, not the assumed one. |
| SQLite single-writer contention between Ruby and Rust. | M1 write-ownership partition: one writer per row-space; the log is append-only; WAL for concurrent reads. |
| SQLite on a network filesystem corrupts. | Out of scope by rule — file sharing is same-host only; cross-host is RES-over-the-wire. |
| Browser WASM can't load the extension. | S4 fallback to Oxigraph-WASM directly; the fast path holds either way; document which. |
| Replay cost grows unbounded (browser cold start). | S3 snapshots + bounded tail. |
| Eventual-consistency surprises (browser shows stale state). | Strong consistency within the host (file/WAL); the browser tier is explicitly a replica with a measured staleness window (S2); writes always round-trip to Ruby's gate, so the user never *commits* against stale local state. |
| Projection drift (a tier's store diverges from the log). | The log is authoritative; periodic snapshot-vs-rebuild parity check; any tier can be rebuilt from the log at any time. |

## Acceptance signal (what would answer the question "yes" for real)
1. **S1:** a Ruby-written event is queryable in the Rust tier within one
   tail cycle, with zero wire between them (same-file read).
2. **S2:** a benchmark table shows the hot operations measurably faster on
   Rust and/or browser-WASM than Ruby-direct, with the staleness window
   quantified.
3. **S3:** a cold browser reaches current state via snapshot + bounded
   tail, not full-history replay.
4. **S4:** a browser answers a SPARQL SELECT over an OPFS-backed store
   (extension-in-WASM *or* Oxigraph-WASM — documented).
5. **S5:** a written decision on RES-replay-only vs persistent-backend,
   with the trade-off measured, not assumed.
6. The architecture diagram above is realized end-to-end for **one**
   representative read (e.g. "what's in my neighborhood?"): governed write
   in Ruby → RES → Rust projection *and* browser projection → answered at
   each tier's locality.
