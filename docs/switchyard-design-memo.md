# NVIDIA NeMo Switchyard as threedot’s LLM-Assistance Plane

Executive summary
- NVIDIA NeMo Switchyard is an open-source Rust-based proxy and library that routes LLM requests across multiple model providers, translates between OpenAI and Anthropic API formats, and exposes routing algorithms with observability hooks. It is designed to enable system-of-models architectures and to sit as an application-layer routing plane that can target local (on-host) or remote (provider) LLM backends. This project is publicly documented as open-source, with ongoing development (pre-alpha) and a maturity caveat about API/algorithm evolution. These properties position Switchyard as a candidate integration point for threedot’s CID-grounded LLM assistance plane, while mandating that the CID contract and local policy boundaries remain under MM’s control. > Quote: "Switchyard lets LLM applications route traffic across models and providers while preserving native OpenAI and Anthropic API compatibility" [2]

1) What NVIDIA Switchyard actually is (status, purpose, APIs, and ecosystem)
- Switchyard is a real, open-source project from NVIDIA that provides a Rust-based proxy plus a library for routing LLM traffic across providers, with protocol translation between OpenAI Chat, Anthropic Messages, and OpenAI Responses formats. It supports multiple routing strategies (random, LLM-classifier, stage-router, etc.) and emits operational metrics suitable for Prometheus/OpenTelemetry integration. It is described as a pre-alpha, experimental project that is evolving rapidly toward a v1.0 target. The project is available on GitHub and is accompanied by official NVIDIA blog coverage that discusses its role in model routing, cost control, and workload balancing. [2] [3] [4] [5] [9]
- In NVIDIA’s ecosystem, Switchyard sits alongside and can route to various inference backends, including NVIDIA’s NIM, and other provider endpoints behind a unified API, performing protocol translation and routing while leaving the underlying transport, credentials, and model invocation to the host or upstream providers. This distinction is key to understanding how threedot can place Switchyard as an integration plane without surrendering policy and secret ownership to the router. [2] [7] [8] [9]
- NVIDIA describes three native execution paths for Switchyard: a launcher path (CLI), a standalone server, and an embeddable library (switchyard-libsy). This separation supports embedding routing logic into an existing gateway or proxy while preserving a provider-neutral surface for clients. The project’s architecture emphasizes routing decisions, policy, and telemetry, while the underlying LLM backends may vary (OpenAI, Anthropic, NIM, vLLM, etc.). [3] [4] [5]

2) threedot—Develop and RUN: how the same Switchyard-enabled plane serves two modes
- threedot exposes a two-tab model in its UI: Develop (Develop) and RUN (Run). Both modes funnel through the same Switchyard-enabled plane but differ in grounding and side effects: Develop uses a CID-driven, draft ground truth to assist in syntax, coding, and shapes; RUN uses an immutable, released CID with an ExecutionEnvelope, enabling runtime assistance with policy-bound decisions. The design aims to keep a single routing plane but with explicit grounding rules per mode to prevent confusion and leakage between workspace drafts and live pod state. [3] [4] [5]
- The CID contract boundary enforces closed, CID-grounded reasoning: a compiled Effective Switchyard Config is produced from the CID declaration and the local target catalog; the plan is to route through the local MLX KV realization or a trusted remote provider based on policy. The Run path binds to an immutable CID release digest and an ExecutionEnvelope, whereas Develop may carry a draft CID and a different grounding surface. This separation supports a “ Flexible Determinism” approach, where the decision substrate is stable and auditable, but LLM output remains stochastic. [1] [4] [6]
- For observability, mmg-observe wraps Switchyard calls with OpenTelemetry spans and metrics, ensuring every LLM call is instrumented (model, source local/remote, latency, tokens, route decision, outcome) and all traces maintain grounding references and policy context. This aligns with GenAI semantic conventions and the OpenTelemetry GenAI community discussions about instrumenting GenAI operations. [10]

3) CID Config ↔ Switchyard contract machinery: contract boundary, config schema, and request/response envelope
- The CID boundary prescribes the allowed assistance via a CID, which includes JSON-LD @context, operation manifest, and closed SHACL shapes. The intended integration pattern is that mmg-switchyard compiles this CID into an immutable Effective Switchyard Config, which then governs the routing decision, target selection, and execution envelope. The config gates what is allowed (model, source local/remote, budget, routing policy) and ensures no secrets or endpoints are leaked via the CID. This mirrors the policy-separated model in NeMo Relay’s architecture (Switchyard handles routing decisions; Relay handles credentials and observability). [2] [4] [5] [6]
- A minimal, illustrative contract structure was drafted to reflect fields like contract_version, config_id/digest, cid with release/draft digests, grounding references, route_policy, privacy, budget, and response_contract. The idea is to provide a sealed, immutable bound that guarantees auditable decision-making and never-raise envelopes. The same architecture is intended to support a local/remote target catalog and to ensure the host retains control of dispatch/credentials while Switchyard handles routing logic. [4] [6]
- The OpenTelemetry instrumentation model recommends tracing attributes around the CID compilation, grounding, routing decision, target call, and response validation. GenAI semantic conventions (gen_ai.*) demonstrate the kinds of attributes to consider for operation, provider, model, tokens, timing, and grounding. mmg-observe should map to those conventions while redacting sensitive content by default and applying policy-driven data minimization. [10]

4) Local vs remote routing and trust: policy boundaries and data-doctrine
- Switchyard provides a provider-neutral routing surface; local routing can be realized via an on-pod KV-backed MLX realization, while remote routing may target a provider such as OpenAI, NVIDIA NIM, or other approved endpoints behind a Switchyard proxy. The choice is guided by the CID policy’s privacy and budget constraints, as well as groundings defined by the ground-rendering component. This separation aligns with NVIDIA’s decomposition between model-serving (NIM, Dynamo, Triton) and the routing plane (Switchyard). [2] [7] [8] [9]
- The “private vs portable” doctrine and trust-ladder discipline are enforced at the CID contract level. Private data must remain local unless explicitly permitted by the CID policy; portable data may be routed to remote targets only if the policy permits and budget allows. The routing engine uses a deterministic scoring tuple to select among candidates and records the decision trace. This approach keeps policy decisions auditable while preserving the flexibility to route to a remote model when allowed. [4] [6]

5) OTEL instrumentation: mmg-observe and GenAI conventions
- Instrumentation is performed by a dedicated mmg-observe wrapper around Switchyard calls. Each LLM call is captured as a span with attributes for model, source (local/remote), tokens, latency, and route decision, along with grounding references and policy evidence. GenAI semantic conventions provide a template for gen_ai.* attributes such as operation.name, provider.name, request/response tokens, time-to-first-token, and content events. The conventions emphasize privacy and data-redaction requirements; mmg-observe should redact sensitive content by default and only expose necessary metadata. [10] [4]
- The Switchyard server itself publishes Prometheus metrics for routing and model calls; in the MM integration, these metrics would be mirrored or integrated through the mmg-observe telemetry surface, with a focus on traceability, budget accounting, and per-route statistics. [5]

6) The mmg-switchyard gem: design, MCB surface, and minimal proof flow
- The mmg-switchyard gem is designed as a private boundary layer that translates the CID policy into an Effective Switchyard Config, chooses between local and remote targets, orchestrates the LLM call, validates the response against the contract, and returns a never-raise envelope. The gem exposes a single MCB surface (mmg.switchyard.assist) and relies on a small surface area for adapters (local MLX, remote clients, NVIDIA Switchyard adapter) with an implementation that ensures no direct secret handling in the gem. The implementation emphasizes strict separation: contract/grounding/route/policy gating in the gem, while transport and endpoint invocation happens in adapters or host runtimes. A minimal proof involves a local + remote routing scenario, with OTEL spans capturing the end-to-end flow and a validated response that adheres to the defined shape. [2] [3] [4] [6]
- The architecture diagram (provided as assistance_plane.mmd and rendered as assistance_plane.png) demonstrates the end-to-end flow: Develop/RUN tabs feed into a CID contract compiler, policy gates route through the mmg-switchyard router to local or remote backends, then to a Never-Raise envelope, with mmg-observe capturing traces. The diagram provides a holistic view of the integration points and the policy boundaries between threedot, CID, and the Switchyard integration. See the included diagram file assistance_plane.png. [3] [4] [5]

7) Minimal proof and build sequence (plan for verification)
- The first proof should be hermetic and use fakes for local MLX and remote adapters to ensure deterministic routing outcomes. The test should verify that local/private paths do not leak to remote endpoints when policy forbids it, that portable routes can succeed with a remote endpoint, and that the envelope is never raised for standard operation. The test harness should also verify that the CID contract compilation, grounding rendering, route decision, and response validation all produce a valid ResultEnvelope. [4] [6]
- A staged build sequence is proposed: contract foundation, MCB vertical slice, local OOCE routing, portable remote routing, observability hardening, NVIDIA adapter integration, threedot UX integration, and operability release. This sequence ensures privacy/never-raise guarantees are established before introducing external Switchyard dependencies. [4] [6] [10]
