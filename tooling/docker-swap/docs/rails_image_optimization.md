# Optimizing Docker Images for Closely Related Rails Services

## Recommendation

When Rails services share the same codebase and differ only by one to three gems, make their **common Ruby runtime, OS libraries, and common bundle a single immutable parent image**, then build each service image `FROM` that exact parent digest. Docker stores common image layers once on a host, so the ten service images will consume the shared base and common-gem layers only once; each service should add only its few unique gems, its code/configuration delta, and its writable container layer.[1]

> The key is not merely having similar Dockerfiles. Every service must inherit from the **same parent image digest** and must preserve exactly the same gem versions for common dependencies.

## Choose between two designs

| Design | Best when | Storage result | Principal trade-off |
|---|---|---|---|
| **One superset image** | The 1–3 differing gems are modest and have no conflicting dependencies | Best possible: one image for all services | All services deploy together and carry each other’s optional gems |
| **Shared common-base + thin service images** | Services need separate versioning, security boundaries, or deployment cadence | Nearly as good: large base layers shared once, small unique layers per service | Maintain a common Gemfile/lockfile contract |

For only a handful of small, non-conflicting gems, start by evaluating the **one superset image**. The extra installed-but-unused gems generally add disk use but do not create meaningful runtime memory cost unless application code requires them. Keep the shared image if the services can safely release together.

If services must be independently released, use the **common-base pattern** below.

## 1. Make common dependencies deterministic

Maintain `Gemfile.common` and its lockfile as the contract for every service. Pin the Ruby version, source(s), platforms, and common gem versions. Each service Gemfile must preserve those versions exactly and only add its own gems. If a service resolves a different version of a supposedly common gem, Bundler can modify/reinstall it and you lose the intended layer sharing.

```ruby
# Gemfile.common
source "https://rubygems.org"
ruby "3.3.6"

gem "rails", "~> 7.2.0"
gem "puma", "~> 6.4"
gem "pg", "~> 1.5"
gem "redis", "~> 5.3"
# all truly shared gems go here
```

For a service, either generate a full lockfile that retains these resolved versions or use a small service-specific Gemfile generated by your build tooling. The crucial invariant is **the shared gem set resolves identically**.

## 2. Publish an immutable common runtime image

Build and push the common image once per change to `Gemfile.common.lock`, the Ruby version, or required runtime library set. Tag it with an immutable identifier, such as the Git SHA of those inputs; do not use a floating `latest` tag in downstream Dockerfiles.

```dockerfile
# Dockerfile.common
# syntax=docker/dockerfile:1.7
ARG RUBY_VERSION=3.3.6
FROM ruby:${RUBY_VERSION}-slim

ENV RAILS_ENV=production \
    RACK_ENV=production \
    BUNDLE_DEPLOYMENT=1 \
    BUNDLE_WITHOUT="development:test" \
    BUNDLE_PATH=/usr/local/bundle \
    BUNDLE_JOBS=4 \
    BUNDLE_RETRY=3

WORKDIR /app

# Keep only libraries required while the application is running.
RUN apt-get update \
 && apt-get install --no-install-recommends -y \
      ca-certificates curl libpq5 \
 && rm -rf /var/lib/apt/lists/*

COPY Gemfile.common Gemfile
COPY Gemfile.common.lock Gemfile.lock

# Cache mount accelerates repeated builds but is not retained in the image.
RUN --mount=type=cache,target=/root/.gem \
    bundle install \
 && bundle clean --force \
 && rm -rf /usr/local/bundle/cache

RUN useradd --create-home --shell /bin/bash rails
USER rails
```

Build it with a content-based tag, for example:

```bash
docker buildx build \
  --push \
  --tag registry.example.com/acme/rails-common:gemset-<git-sha> \
  --file Dockerfile.common .
```

Multi-stage builds are also appropriate if building a gem or assets needs compiler packages that should never be present in the runtime image. Docker supports selectively copying build artifacts from one stage to another, leaving build-only content behind.[2]

## 3. Make each service image a thin child

Each service image uses the exact common image as `FROM`, installs only its delta gems, and copies only its code/configuration. When a service has native gems, install compiler headers and remove them **within the same `RUN` instruction** so they are not committed as a separate image layer. Retain only the runtime shared libraries required by those gems.

```dockerfile
# services/billing/Dockerfile
# syntax=docker/dockerfile:1.7
FROM registry.example.com/acme/rails-common:gemset-<git-sha>

USER root
WORKDIR /app

# This Gemfile.lock must retain all versions from Gemfile.common.lock,
# plus only the service-specific gems.
COPY services/billing/Gemfile services/billing/Gemfile.lock ./

RUN --mount=type=cache,target=/root/.gem \
    apt-get update \
 && apt-get install --no-install-recommends -y \
      build-essential pkg-config libpq-dev \
 && bundle install \
 && bundle clean --force \
 && apt-get purge -y --auto-remove build-essential pkg-config libpq-dev \
 && rm -rf /var/lib/apt/lists/* /usr/local/bundle/cache

# Copy application source after dependency installation: normal source changes
# then do not invalidate the gem layer.
COPY --chown=rails:rails . .

USER rails
ENV RAILS_LOG_TO_STDOUT=1 \
    RAILS_SERVE_STATIC_FILES=1
CMD ["bundle", "exec", "puma", "-C", "config/puma.rb"]
```

In practice, replace `libpq5`, `libpq-dev`, and the compiler list with the smallest runtime/build package set your gems require. Do not use `apk`/Alpine solely for a smaller base unless your native dependencies have been tested against musl; `ruby:3.3.6-slim` is usually the lower-risk Rails baseline.

## 4. Preserve the cache and limit the build context

Copy `Gemfile` and `Gemfile.lock` before application source. Docker reuses a cached layer when its instruction and dependent files are unchanged; placing dependency installation early prevents ordinary source edits from re-running `bundle install`.[3] A BuildKit cache mount for Ruby gems also makes a cache miss cheaper because unchanged downloads can be reused.[3]

Use a strict `.dockerignore` file. Docker sends the build context to the builder, and excluding files that are unnecessary to the image reduces transfer time and accidental cache invalidation.[3] A Rails baseline is:

```gitignore
.git
.github
log/*
tmp/*
coverage/
spec/
test/
features/
node_modules/
vendor/bundle/
vendor/cache/
public/assets/
public/packs/
.env
.env.*
Dockerfile*
docker-compose*.yml
README.md
```

Keep tests in CI rather than shipping them to production. Exclude generated development assets only if your build pipeline recreates or supplies the required production assets.

## 5. Do not turn code or databases into per-container disk growth

Keep logs on standard output and configure Docker log rotation. Store uploads, database data, caches, and queues in volumes or external services—not inside the application container’s writable layer. Docker’s copy-on-write storage makes multiple containers efficient when they share read-only layers, while containers that write heavily accumulate data in their own writable layers.[1]

## 6. Verify that the desired sharing actually occurred

On the VPS, inspect real shared versus unique image storage rather than adding the displayed size of every image:

```bash
# Image-level shared and unique storage
sudo docker system df -v

# Each container's writable layer; exclude virtual image size from comparisons
sudo docker ps --size

# Confirm that the child images actually use the same layer IDs
sudo docker image inspect \
  registry.example.com/acme/rails-common:gemset-<git-sha> \
  registry.example.com/acme/billing:<release-sha> \
  --format '{{.RepoTags}} {{json .RootFS.Layers}}'
```

`docker system df -v` reports `SHARED SIZE` and `UNIQUE SIZE`; Docker defines the image’s displayed `SIZE` as their sum.[4] Do not sum each container’s virtual size: shared read-only image layers can be counted repeatedly by that figure.[1]

## Expected outcome

With this layout, the disk cost on each VPS is approximately:

| Component | Stored once? | Expected change per service |
|---|---:|---|
| Ruby base image, OS runtime libraries | Yes | None |
| Rails and common gems | Yes | None |
| 1–3 service-specific gems | No | Small extra layer, unless a gem pulls large native dependencies |
| Application code / compiled assets | No, unless one superset image is used | One service code layer |
| Logs, cache, temporary files | No | Potentially unbounded without log rotation and volumes |

The largest savings come from a shared common bundle, immutable parent digests, correct Dockerfile layer order, and preventing runtime writes from accumulating in container layers. **Do not expect a large RAM reduction solely from image-layer sharing**: it primarily optimizes disk and pull bandwidth. RAM must still be sized for the Rails/Puma processes, workers, and databases that actually run.
